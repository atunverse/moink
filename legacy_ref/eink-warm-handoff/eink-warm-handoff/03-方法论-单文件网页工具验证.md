# Verifying single-file web tools

Self-contained HTML tools are shipped as one blob, so a silent transcription bug in the
math or an encoder only shows up as "the output looks slightly off". Two test layers
catch this, and both are cheap to set up.

**Layer 1 — algorithm agreement.** Keep one authoritative implementation (usually Python +
numpy, because it is fast to iterate and easy to inspect), and treat the JS in the HTML as
a port. Extract the JS *from the shipped file* — never from a copy — run it in Node, and
compare outputs numerically. This turns "looks right" into "0 differing pixels".

**Layer 2 — page behaviour.** Drive the real page in headless Chromium: import a file,
sweep every control, click every export button, capture the download, and decode the
downloaded artefact with an independent library. This is the only way to catch
`<details>`-hidden controls, resampling mistakes, and hand-written encoders that produce
files other tools reject.

## Layer 1 workflow

1. **Write the reference first**, and generate a deterministic test input plus expected
   output for a spread of parameter combinations, not just the defaults. Cover: every
   mode/branch, both ends of every slider, and toggles on and off. Write expected values as
   raw binary (`float64`/`uint8` via `.tofile()`), not JSON — JSON round-tripping of floats
   destroys the comparison.

   **Always include at least one case per branch with the branch's own parameters pushed off
   their defaults.** A case that only exercises defaults can pass while a non-default sibling
   is completely wrong: if two stages commute at a neutral parameter value (saturation 1.0,
   gain 0, angle 0) then swapping their order is invisible until the parameter moves. Two
   cases differing in exactly one probe parameter is what exposes it.

2. **Make the JS callable from outside.** Expose the pure functions on a window property at
   the end of the script, e.g. `window.__tool = { warmMapFlat, ditherFlat, statsFromIndex }`.
   Keep them free of DOM access so they can run headless.

3. **Extract and execute in Node** with `vm`. Read the HTML, pull the script blocks with a
   regex, take the last one, and run it inside a context whose `document`/`window` are
   catch-all `Proxy` stubs. `scripts/extract_and_run_js.mjs` is a working template. The
   point of running the whole script rather than a pasted-out copy is that the UI wiring
   also executes, so a typo'd element id or a missing function surfaces immediately.

4. **Compare and fail loudly.** Report per case: share of exactly equal floats, max absolute
   delta, and — most important — the number of differing output samples. For quantised
   output (palette indices, bit-packed data, final file bytes) require *zero* mismatches.
   Accept a residual float delta below ~1e-9 as last-bit `libm`/V8 rounding; anything larger
   is a logic difference, and any index mismatch at all is a bug.

5. **Read the magnitude of the disagreement, not just its existence.** It tells you which
   class of bug you have, and that decides where to look:

   | symptom | almost always |
   |---|---|
   | every case exact, one case wildly off (Δ of tens) | stage **order** differs, or a stage is missing entirely — compare the sequence of operations, not their arithmetic |
   | a handful of pixels off by a lot, at a specific value (a hue, a threshold) | a **hard branch switch** (`if x > T`) where the two sides handle the seam differently; the two languages land on opposite sides of `T` because of a 1e-16 difference |
   | a large share of samples off in the last 2-3 bits | rounding/modulo/parenthesisation — real but harmless; check the quantised output before caring |
   | an entire case exact, the next case 0% exact | the differing case exercises a branch the passing one does not (a different mode, or a parameter at a non-neutral value) |

   When you find a hard branch switch, prefer replacing it with a weighted blend of both
   terms (`hd + (1-w)*a + w*b`) over keeping the `if`. A blend is continuous, so a last-bit
   difference stays a last-bit difference instead of flipping a pixel by a visible amount —
   and the artefact is usually a real quality bug too: a discontinuity in a smooth gradient
   shows up as a contour line in the output.

## Layer 2 workflow

1. Install once: `pip install playwright` then `python -m playwright install chromium`. On
   Windows expect a harmless `[safe-delete]` / `ETIMEDOUT` message at the end of the browser
   install — check for `INSTALLATION_COMPLETE` in `%LOCALAPPDATA%\ms-playwright\chromium-*`
   and proceed.
2. Open the page with a `file:///` URL. Register `page.on("pageerror")` and
   `page.on("console")` and assert zero errors at the end — this is the cheapest possible
   smoke test for a large inline script.
3. **Expand collapsed containers before touching their controls.** Selects inside
   `<details>` are not visible, and Playwright's `select_option` / `fill` wait for
   visibility and then time out. Run
   `page.evaluate("() => document.querySelectorAll('details').forEach(d => d.open = true)")`
   right after load.
4. Feed images through the real input element with `page.set_input_files("#file", path)`
   rather than injecting JS — it exercises the same code path a user hits.
5. Assert the rendered result by reading the canvas: `getImageData`, histogram the distinct
   colours, and check that the expected palette accounts for 100% of pixels. "0 off-palette
   pixels" is a far stronger statement than a screenshot.
6. For exports, use `with page.expect_download() as dl:` and `f.save_as(path)`, then decode
   the saved file with an independent library (PIL) and re-check the histogram. For binary
   formats also assert the byte length against the hand-computed expectation
   (`ceil(w*bpp/8)*h`) and unpack it to confirm the values land in range.
7. Re-run the same page at a phone viewport (e.g. 412x915) and assert
   `documentElement.scrollWidth <= clientWidth` to catch horizontal overflow.
8. **Assert computed style, not the `hidden` attribute, when toggling panels.** An author rule
   like `.two{display:grid}` outranks the user-agent `[hidden]{display:none}`, so `el.hidden = true`
   silently does nothing and controls belonging to another mode stay on screen. Fix it once with
   `[hidden]{display:none !important}` and test with
   `getComputedStyle(el).display`, which is the only thing that reflects what the user sees.
9. **Exercise the awkward sizes, not just the friendly ones.** If a hand-written packer works
   in 4-pixel groups (4bpp/2bpp image data, nibble-packed rows), test a width that is *not* a
   multiple of 4 so the half-filled tail byte is hit — `750x502` catches an off-by-one that
   `768x552` never will. If the size is only reachable through a `step=8` slider, the tail path
   is unreachable from the UI: loosen the step or test through the JS API.
10. **A file size that does not change when the image does is a bug report.** If two different
    photos export to the *same byte count*, the encoder is emitting stored/uncompressed blocks
    (constant overhead) rather than compressing. Check the IDAT path; in a browser, prefer
    `CompressionStream('deflate')` (zlib-wrapped, exactly what IDAT wants) with a stored-block
    fallback, and note that this makes the export path `async`.

## Porting rules that keep the two implementations identical

These are the specific things that broke pixel-exactness in practice. Follow them when
writing the JS side:

- Iterate a **flat `Float64Array`/`float64` buffer** (row-major, 3 or 4 channels interleaved)
  rather than nested loops over objects. Layout stops mattering and the code ports by
  copy-paste.
- Match **rounding**: use `Math.floor(x + 0.5)`; never `Math.round` (half-away-from-zero vs
  numpy's behaviour) and never `np.round` (banker's rounding) on the other side.
- Match **modulo**: Python's `%` on floats already behaves like a Euclidean modulo, JS's does
  not. Port it as `((a % n) + n) % n` and use it for every wrap (hue, phase, angle).
- Reproduce library formulas **term for term**. `numpy.interp` computes
  `(y1-y0)/(x1-x0) * (x-x0) + y0`; a mathematically equivalent but differently ordered
  expression gives a different last bit.
- Guard **both** sides identically: if one side clips to `0..255` at the end of a stage, the
  other must too. A missing final clamp changes error-diffusion input and shifts the output
  by a visible amount.
- Index derived lookups (gradient ramps, transfer curves) with the value of the **same stage**
  on both sides. Deciding which intermediate to key a lookup off is easy to do differently in
  each language; make the choice explicit in a comment.
- When refactoring the reference for speed, keep the mode/branch table intact — dropping a
  branch during a rewrite is a classic silent regression.
- **Re-check the order of the pipeline stages after any rewrite**, and leave a comment
  wherever two stages commute at a neutral value. "Blend toward a gradient, then apply the
  chroma gain" and "apply the chroma gain, then blend" are the same picture at gain 1.0 and
  visibly different at gain 1.9 — which is exactly why a defaults-only test suite misses it.

## Worked example

Everything above was established while building the 4-colour e-ink converter at
`project\` (`gen_test.py` +
`verify_vs_js.mjs` for layer 1, `test_e2e.py` / `test_edge.py` / `check_exports.py` for
layer 2). Copy those five scripts as a starting skeleton. They caught, in one session:
swapped pipeline stages invisible at default parameters, a hard hue-threshold branch that
flipped pixels on a 1e-16 difference, a branch dropped during a refactor, an uncompressed
deflate stream, and a size slider whose `step` made a bit-packing edge case unreachable.

Layer 1 is what catches logic bugs; layer 2 is what catches wiring, encoder and UI bugs.
**Running only one of them is why "it looks fine" ships broken.**
