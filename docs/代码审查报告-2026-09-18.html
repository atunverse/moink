页面问题清单（按优先级）

P1 功能性缺陷（用户可感知）

编号位置问题影响建议改法与安全性
P1upload() 错误分支（xhr.onload 内） msg("上传失败：" + xhr.responseText || xhr.status) —— + 优先级高于 ||，前半截永远为真字符串，||xhr.status 永不生效；且 body 为空时只显示「上传失败：」没有原因。 上传失败时用户看不到服务端原因（如 "CRC mismatch"/"busy"），排障困难。 改为 "上传失败：" + (xhr.responseText || ("HTTP " + xhr.status))。纯字符串拼接改动，零功能风险。
P2saveOffline 导出 document.documentElement.outerHTML 序列化的是运行时 DOM：#ctrls 里 13 个动态滑块、tFont 的 4 个 option、objLayer 的手柄 div、各按钮/页签的 class 都被打进导出文件。重新打开时初始化代码再生成一遍 → 高级滑块和字体选项翻倍；objLayer 残留 div 依赖 layoutObjs 数量对齐才侥幸正常。 导出的离线客户端界面元素重复（滑块×2、字体项×2），且任何未来「按索引取控件」的逻辑都会错位。 导出前 cloneNode(true) 一份干净 DOM：清空 #ctrls、移除 tFont 多余 option、清空 #objLayer、把 tab/steps/mode 的动态 class 复位，再序列化克隆体。不动运行中的原 DOM，功能零影响。
P3syncSel() 描边回显 $("tStrokeC").value = String(+o.strokeC === 0 ? 0 : 1) —— R1.0.19 已支持四色描边（0黑/1白/2黄/3红），但选中回显把黄/红折叠成白。用户选「黄边」→ 消失再选中 → 下拉框显示「白边」；此时碰一下该下拉就会把对象真值改写成 1。 四色描边的回显失真 + 意外改值。 改为 String(clamp(+o.strokeC|0,0,3))。一行修复。

P2 健壮性 / 边界

编号位置问题影响建议改法与安全性
P4loadFile() EXIF 烤正兜底 cv.toBlob 成功后先 URL.revokeObjectURL(url) 再加载烤正图；若 im2.onerror 兜底回 adoptImg(im, url, f)，此时 url 已被吊销 → 缩略图与 Cropper 重新加载都会失败。 极小概率（Blob 解码紧接 canvas 编码失败），但一旦命中整条图像管线瘫痪且无提示。 把 revoke 挪到 im2.onload 内；adoptImg 内部「imgUrl !== url 才 revoke」的保护保留。时序后移，无副作用。
P5upload() / postFileTo() XHR 无 timeout。设备若在接收中卡死（SoftAP 弱信号、固件忙），xhr 永远 pending，上传按钮保持禁用。 偶发「点不动上传」，只能刷新页面。 xhr.timeout = 60000; xhr.ontimeout = 与 onerror 同。超时只是兜底，正常路径不受影响。
P6exifOrientation() d.getUint32(off+4) 只受外层 off+4 < byteLength 保护，末尾截断的 JPEG 可能抛 RangeError——目前靠调用方 try/catch 兜住（能兜住，但属隐式依赖）。 无实际故障，可读性/防御性问题。 读取前加 if (off + 8 > d.byteLength) break;。零行为变化。
P7odMove 多点触控 pointermove 监听在 document 上、不校验 e.pointerId，第二根手指（掌缘误触）会叠加位移，拖动中的文字会跳。 手机上偶发拖动跳变。 pointerdown 记录 od.pid = e.pointerId，odMove 首行 if (e.pointerId !== od.pid) return;。单指行为完全不变。

编号问题建议
P8modeAR() 全页无调用（R1.0.12 起退役）删除（smoke 同步确认）。
P9CTRL 表 unit:"×"/"°" 字段已不参与显示（只剩 ==="%" 判断）把 unit 字段收窄为 pct:true/false，语义更清晰；或保留并注释「仅 % 有意义」。

内存与资源结论

  • ✅ 无泄漏：blob URL 的创建/吊销配对完整（仅 P4 时序瑕疵）；cropCache、_rampCache、liveBase 均有明确失效路径（odUp/cropInvalid/destroyCrop）。
  • 事件监听：odMove/odUp 在 odUp 成对摘除；但若拖动中页面进入后台，pointercancel 已监听，覆盖到位。
  • 峰值内存：见「效率」页 F 侧建议，Float64Array 全链换 Float32 可把预览峰值从约 40MB 降到 20MB，对老手机意义大。

固件问题清单（按优先级）

P0 并发互斥缺失

编号位置问题影响建议改法与安全性
F1main.c clear_handler → epd_clear_cycles 残影清理直接驱动 panel：用 epd_drv.c 的 static row[]（与 frame_task 正在用的 epd_write_frame_* 同一块静态缓冲）、同一 SPI 总线、同一组 CS/DC GPIO。frame_task 是独立 FreeRTOS 任务，frame_upload_handler 只锁了 s_fb_mutex 保护帧缓冲本身，clear 路径完全不经过这把锁。 用户在清理残影（最长 2~4 次全刷，约 40~120 秒窗口）期间传图 → 两个任务交替向面板发命令/数据，SPI 时序交错 → 画面花屏，且两个流程都会「以为自己在正常刷屏」。 把 s_fb_mutex 的能力导出（如 frame.c 新增 frame_lock_display()/frame_unlock_display()，内部就是 xSemaphoreTake/Give(s_fb_mutex)），clear_handler 全程持锁。不改变任何显示时序——单用户场景下 clear 与传图本来就不会同时发生，加锁只是把「碰巧没坏」变成「保证不坏」。改动约 10 行。

P1 内存安全 / 稳定性

编号位置问题影响建议改法与安全性
F2captive.c dns_task 应答缓冲 r[512]：答案段固定追加 16 字节（指针+TYPE+CLASS+TTL+RDLEN+4 字节 IP），而问题段 qend 上限只被 qend > n 拦截，n 最大 512 → a = qend + 16 最多写到 r[527]，栈越界写 16 字节。 构造 512 字节满长 DNS 查询即可踩坏 3KB 的 dns_task 栈。触发条件苛刻（同一 AP 内的设备才会发），但栈损坏的后果是硬崩溃。 进答案段前加一行 guard：if (qend > (int)sizeof(r) - 20) continue;。或把 r 定义为 560 字节。一行修复，DNS 劫持行为完全不变。
F3main.c read_body()（settings POST 用） 单次 httpd_req_recv 不保证收满（TCP 分段短读，frame.c 注释里自己就写过这条经验），settings 的 512B body 可能只收到半截就开始解析 → 后半段字段静默丢失。 弱信号下保存设置偶发「部分保存」，且无任何报错。 read_body 改为循环收满 content_len（照抄 frame.c 的 while 模式），并顺带把超出 n-1 的剩余字节读完丢弃，避免污染 keep-alive 连接。与 frame.c 同构，风险极低。
F4frame.c / ota_web.c 各上传 handler power_activity() 只在 main.c 的 info/settings/clear/factory/page handler 里调用；frame_upload、ota_handler、web_handler、web_clear 都不喂看门狗。手机经 SoftAP 传 106KB 帧约 5~30 秒、OTA 1.5MB 更久；若用户在设备空闲 50 秒后才开始传图（sleep_s=60 档），空闲计时会在上传中途到点 → 深睡。clear_handler 4 周期（约 100~120s）同样超过 60s 窗口。 传输/清理中途设备深睡：传图失败、OTA 靠回滚机制兜底（白等 45s）、残影清理半途而废。 在这四个 handler 入口各加一行 power_activity()；epd_clear_cycles 每周期完成后再喂一次。不改任何休眠策略本身，只是把「有用户活动」这件事说全。

P2 健壮性 / 效率

编号位置问题影响建议改法与安全性
F5ota_web.c ota_web_has_page() 每次 GET / 都全量读 web 分区并逐位算 CRC32（960KB → 约 960 万次位运算 + 全分区 flash 读），页面每次加载平添 100~300ms 响应延迟与 CPU 空转。 每次打开控制页都变慢；期间 httpd 单线程被占住，其他请求排队。 加 static int s_page_ok = -1; 缓存三态（未知/有效/无效）：启动后首次请求算一次，web_handler/ota_web_clear 写完后置位。上传/清除都会重启浏览器会话，缓存一致性天然安全。
F6frame.c frame_upload_handler 只校验 content_len ≥ 16，不校验 == 16 + buf_len。body 带多余尾字节时尾字节不被读走，keep-alive 连接的下一请求解析错乱。 正常页面不会触发（帧长固定）；异常客户端会挂死一条连接。 入口处加 if (req->content_len != FRAME_HDR_LEN + p->buf_len) return 400;。语义更严但完全兼容现有页面。
F7netif_ap_apply() ESP_ERROR_CHECK(esp_wifi_set_config/start) 在运行时改热点路径上——任何返回错误直接 abort 重启。 IDF 对运行中 AP 的 set_config/start 通常返回 OK，风险低；但一旦命中（如 ssid_len 边界）就是无提示重启循环。 这两处改为 esp_err_t e = ...; if (e != ESP_OK) ESP_LOGE(...)。启动路径（netif_ap_init 内首次）保留 ESP_ERROR_CHECK 不动。
F8ota_web.c ota_handler esp_ota_begin(part, total, &h) 会在收到第一个字节前同步整槽擦除（ota_0/1 各 1.5MB，数秒），httpd 单线程被完全占住。 OTA 请求发出后前几秒零响应，浏览器可能先报错；页面提示「上传中」但实际还在擦除。 参照 web_handler 的「按扇区先擦后写」模式流式写 OTA（esp_ota_write 本身按扇区处理，begin 传 USART... 亦可 begin 后逐 4K 预擦）。收益是响应性；因 OTA 已验证稳定，建议低优先级、单独一版只做这一件事。

内存与资源结论

  • ✅ 帧缓冲/信号量：frame_init 一次分配 105984B（malloc，失败 abort 合理——没 framebuffer 就没有产品），mutex/binary semaphore 配对正确，上传持锁有 5s 超时，显示持锁 portMAX_DELAY 但锁内只有驱动时序、无死锁路径。
  • ✅ NVS：全部 open→…→close 配对；恢复出厂按设计保留页面标记（教训⑥已固化）。
  • ✅ OTA 回滚：45s confirm + has_page CRC 自愈，失败路径都有出口。
  • ✅ socket：captive DNS socket 常驻属设计使然，bind 失败分支有 close。
  • 栈余量：httpd 4KB 中 settings handler 栈上约 700B（body 512 + ssid/pass 98 + 杂项），余量可接受但接近历史事故区（教训③），换用 read_body 循环方案时建议顺手把 body 缓冲改静态共享（与 s_buf 同思路）。
