## 2. 版本号统一（★ 本方案核心）

### 2.1 统一后的形态

```c
/* version.h 统一后 */
#define MOINK_API_VERSION   2           /* 帧格式契约号：与发布版本号解耦，保持 2 */
#define MOINK_VERSION       "R1.2.0"    /* 唯一版本号：固件与页面共用这一个 */
```

- 删掉 `MOINK_FW_VERSION`、`MOINK_PAGE_VERSION` 两个宏。
- **`api` 必须保留**：它是**帧格式契约号**（`hdr[2]` 载荷几何 768×552 / 800×600），是判断「旧页面发来的帧还能不能收」的唯一锚点，与发布版本号是两件事。它**不对外显示为「版本」**，页面状态栏另有一行「接口」。

### 2.2 编号推进规则（沿用现有节奏，只是不再分叉）

| 变更类型 | 动作 | 示例 |
|---|---|---|
| 破坏性：分区表 / NVS 布局 / 屏驱动基线 / 帧格式契约 | **主版本 +1**，后两位归 0 | R1.x.x → **R2.0.0** |
| 固件功能：新接口、新路由、新能力 | **次版本 +1**，第三位归 0 | R1.1.3 → **R1.2.0** |
| 修复 / 纯页面变更（含热更） | **第三位 +1** | R1.2.0 → **R1.2.1** |

> 与原项目规则完全一致（bug 批第三位 +1、功能批第二位 +1、契约变化 api+1），只是 fw / page 两条线合成了一条，**不会再有 `fw R1.1.1 / page R1.1.3` 这种错配状态需要解释**。

### 2.3 运行时「当前版本」怎么取

页面可热更 ⇒ 设备上「当前在跑的页面」版本可能**领先**固件里编译进去的号（这正是需求 B 描述的现象）。因此：

```c
/* 语义由「页面版本」升格为「当前生效版本」：
   有热更页 -> 用热更页 meta 里解析出的号；否则 -> MOINK_VERSION */
const char *ota_web_page_version(void);   /* 函数名保留，实现不变 */
```

`GET /api/info` 返回：

```json
{"ver":"R1.2.1","fw":"R1.2.0","page":"R1.2.1","upload":1,"api":2, "panel":"A1", ...}
```

| 字段 | 含义 | 用途 |
|---|---|---|
| `ver` | **统一版本号** = 当前生效页面版本（≥ 固件版本） | 页面状态栏、用户唯一需要看的号 |
| `fw` / `page` | 保留一版（诊断用，值分别 = 固件编译号 / 生效页面号） | 排障；旧页面仍读得到 |
| `upload` | `1` = 固件支持 `/api/upload` 统一入口 | 页面据此决定走单入口还是双入口回退（见 §3.4） |
| `api` | 帧格式契约号 | 不变 |

### 2.4 界面上的体现

状态面板「固件 / 页面 / 接口」三行 → **两行**：

```
版本      R1.2.1
接口      2
```

页脚 `页面 x.y.z` → **`版本 x.y.z`**（仍由 `<meta name="moink-page-version">` 运行时填充）。

### 2.5 防止两处版本号漂移（门禁）

统一为「一个版本号」后，最大的隐患是 **`version.h` 与页面 meta 各写一份、日久漂移**（那就又变回两套号了）。做法：

**`tools/make_index_header.py` 固化前加断言** —— 从 `page/index.html` 抽出 `<meta name="moink-page-version" content="...">`，与 `src/version.h` 的 `MOINK_VERSION` 比对，**不一致直接 `exit 1`**，并在终端打印两边实际值。

这样「页面号 / 固件号」在编译期就被强制锁死；热更页面造成的运行时超前是**允许且被显示**的唯一例外。

## 3. 升级入口合并

### 3.1 交互形态

「系统维护与升级」里的 **① 固件（.bin）** 与 **② 页面（index.html）** 两个区块，合成**一个**：

```
① 升级
  [ 选择文件 ]                      ← accept=".bin,.html,.htm"
  [ 上传并升级 ]
  上传 .bin  = 固件升级（控制页一并更新，设备会自动重启）
  上传 .html = 仅更新控制页（不重启，刷新浏览器即可）
  [清理残影]  [下载离线客户端]
```

- 删掉「同步更新页面」复选框 —— 固件升级**总是**同步页面，复选框失去意义（就是 FB-012 那个补丁的语义，现在变成默认行为）。
- 「恢复内置页面」保留，放在同一区块下方（应急回滚用）。

### 3.2 文件类型识别规则（固件端与页面端**同一套规则**）

| 判定 | 条件 | 分流 |
|---|---|---|
| 固件 `.bin` | 第 1 字节 = `0xE9`（ESP 镜像魔数） | OTA 路径 |
| 页面 `.html` | 前 1 KB 内出现 `<!doctype` 或 `<html`（大小写不敏感，允许 BOM / 前导空白） | 页面热更路径 |
| 其它 | 都不匹配 | `400` + `unrecognized: expect .bin (ESP image) or .html (control page)` |

**为什么不看文件名 / Content-Type**：
- 页面为了避开跨源预检，一直把文件包成 `text/plain` Blob 再发（旧固件 R1.0.5 之前没有通配匹配）。所以 Content-Type 一律是 `text/plain`，不能用作判据。
- 文件名在 `Blob` 里不带 `filename`，拿不到扩展名。
- 只有**内容魔数**是两端都可靠、且与传输方式无关的判据。

### 3.3 固件侧实现（最小改动）

**新增一条统一路由，旧的两条原样保留**：

```
POST /api/upload   ← 新：嗅探 + 分流（新页面用这条）
POST /api/ota      ← 旧：直接走 OTA（旧页面 / 离线客户端仍在用）
POST /api/web      ← 旧：直接走页面热更
```

做法是把两条既有 handler 的**接收循环各抽出一个「可接受预读首块」的入口**，不重写逻辑：

```c
static esp_err_t ota_stream(httpd_req_t *req, const char *p0, int n0);   /* 原 ota_handler 主体 + 首块 */
static esp_err_t web_stream(httpd_req_t *req, const char *p0, int n0);   /* 原 web_handler 主体 + 首块 */

static esp_err_t ota_handler(httpd_req_t *req) { return ota_stream(req, NULL, 0); }
static esp_err_t web_handler(httpd_req_t *req) { return web_stream(req, NULL, 0); }

/* 统一入口：预读首块 -> 嗅探 -> 分流 */
static esp_err_t upload_handler(httpd_req_t *req)
{
    size_t total = req->content_len;
    if (total == 0) return httpd_resp_send_err(req, HTTPD_400_BAD_REQUEST, "empty");

    /* 累积到 >=64B 再判定（TCP 首段可能很短，"n 很小" 不能作结论） */
    int got = 0;
    while (got < 64 && got < (int)total) {
        int k = httpd_req_recv(req, s_buf + got, sizeof(s_buf) - got);
        if (k <= 0) break;
        got += k;
    }
    if (got <= 0) return httpd_resp_send_err(req, HTTPD_400_BAD_REQUEST, "truncated");

    power_activity();
    int kind = sniff_kind(s_buf, got);      /* 0=固件 1=页面 -1=未知 */
    if (kind == 0) return ota_stream(req, s_buf, got);
    if (kind == 1) return web_stream(req, s_buf, got);
    return httpd_resp_send_err(req, HTTPD_400_BAD_REQUEST,
        "unrecognized: expect .bin (ESP image) or .html (control page)");
}
```

要点：
- **预读的字节必须原样交给下游**（作为写入的第一块），否则文件头丢掉 → 固件魔数校验失败 / 页面残废。`p0/n0` 就是这个作用。
- **判定前不做任何擦写**：识别失败 = 什么都没动，安全。
- `s_buf` 是既有的静态共享接收缓冲（httpd 栈仅 4 KB，禁止栈上放大数组）—— 复用它，不新增内存。

### 3.4 三端兼容矩阵（零破坏）

| 客户端 | 上传固件 | 上传页面 | 结果 |
|---|---|---|---|
| **新页面**（R1.2.0，`upload=1`） | `POST /api/upload` (text/plain) | `POST /api/upload` | ✅ 单入口 |
| **新页面 + 旧固件**（页面被热更到 R1.1.x 固件上） | 回退 `POST /api/ota` | 回退 `POST /api/web` | ✅ 前端按 `j.upload` 缺失自动回退 |
| **旧页面**（R1.1.x，可能是设备上留存的旧页） | `POST /api/ota?sync_page=1` | `POST /api/web` | ✅ 旧路由保留 |
| **旧离线客户端**（`/api/ota` 硬编码） | `POST /api/ota` | — | ✅ 保留 |
| **新固件**收到旧路由 | 照常工作 | 照常工作 | ✅ |

**关键点**：前端必须以 `/api/info` 的 `upload` 能力位决定走哪条路，不能硬编码 —— 因为「新页面被热更到旧固件上」是这个架构下必然会出现的组合。

### 3.5 响应体与前端判定

- `/api/upload` 成功：`text/plain` 回 `"fw"` 或 `"page"`（固件路径 1 秒后即重启，响应**可能收不到**，属已知情形）。
- **前端不依赖响应来判类型**：上传前用 `FileReader` 读文件前 1 KB，按 §3.2 **同一套规则**预判，进度文案直接显示「正在上传固件…」/「正在上传控制页…」；`retcode==200` 只用于确认成功，`400 unrecognized` 才提示重选。这样即便 OTA 重启把响应吞了，用户看到的文案也是对的。

| R1 | **首块嗅探误判** | 中 | 固件当页面写进 web 分区（或反之），升级失败 | ① 累积 ≥64 B 才判定；② 判定前不擦写任何分区；③ 双端同规则 + 上游魔数校验兜底（固件路径仍有 `0xE9`+chip_id+app magic 三重校验）；④ 无法识别直接 400 并给明确文案 |
| R2 | **预读首块丢失**（重构时把 `p0` 漏掉） | 中 | 固件/页面从头就是坏的，且**静默** | 抽公共入口时**断言第一块写入来自 `p0`**；验证包必须实机走一次 `/api/upload` 升固件与升页面各一次 |
| R3 | 浏览器缓存 `GET /` → 以为固件没生效 | 中 | 误判 | `page_handler` 加 `Cache-Control: no-store` |
| R4 | 热更页面版本**低于**固件（用户上传旧 html） | 中 | 版本号倒退，接口可能不匹配 | ① `/api/info` 暴露 `fw`/`page` 供排障；② 页面显示 `ver` 时若 `page < fw` 用黄色警示「控制页版本低于固件，建议重新上传固件」；③ 是否**直接拒收**低版本页面见决策点 D4 |
| R5 | `version.h` 与页面 meta 版本号漂移（又变两套号） | 中 | 回到今天要解决的原点 | `make_index_header.py` 编译前断言（§2.5） |
| R6 | 新页面被热更到旧固件 → `/api/upload` 404 | 中 | 升级按钮失效 | 前端按 `j.upload` 回退旧路由（§3.4） |
| R7 | 用户上传 `.bin` 却以为是升页面（或反之） | 低 | 困惑 | 前端预判 + 明确文案；上传前显示识别结果「已识别为：固件」 |
| R8 | 页面热更后与固件版本号"不对齐"被误解为 bug | 低 | 解释成本 | 文档 + 状态栏小字标注来源（内嵌 / 热更） |
