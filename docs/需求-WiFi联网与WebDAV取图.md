## 1. 需求原文与我的解读

**功能一**：在现有「开机开热点」不变的前提下，增加「连接 WiFi」设置。连上路由器后设备能上网，
用户连它的热点也能上网 —— 不要在连接设备时把用户的手机断网。

**功能二**：基于功能一，定时唤醒后不从 flash 图槽取图，而是连 WiFi → 连 WebDAV → 读指定文件 → 刷到屏上。

这里有一处必须先分清，它决定工作量差一倍：

| 解读 | 含义 | 实现 | 工作量 |
|---|---|---|---|
| A. 手机连设备热点，设备只是「自己也联网了」 | 手机仍无外网，只是设备能拉图 | 仅 APSTA 共存 | 小 |
| **B. 手机连设备热点就能上网（设备当二级路由）** | 设备把 AP 侧流量 NAT 到 STA 侧 | APSTA + **NAPT**（`esp_netif_napt_enable`） | 中 |

按你的描述（「通过连接它的热点来连接网络，不会造成在连接设备的时候用户就断网了」），
我理解你要的是 **B**。技术上成立：ESP-IDF 提供官方 NAPT 接口，ESP32-C3 支持。
但当前工程 `sdkconfig` 里 `CONFIG_LWIP_IP_FORWARD` 是**关闭**的，必须打开才能做转发（§3.4）。

## 2. 现状与硬约束（决定了方案边界）

| 项 | 现状 | 对方案的限制 |
|---|---|---|
| 芯片 | ESP32-C3 SUPERMINI，**无 PSRAM**，约 320 KB 可用堆 | 不能同时握两块 106 KB 帧缓冲；不能整帧 RGB 解码 |
| WiFi 模式 | `netif_ap.c` 里 `WIFI_MODE_AP` + 固定信道 6 | 改 APSTA 后 AP 信道必须跟随路由器信道（同一射频） |
| 静态 RAM | 39,692 B（R1.3.4） | 加 WiFi STA + TLS + NAPT 后要实测余量 |
| 帧缓冲 | `frame_init()` 一次 malloc ≈ 106 KB（768×552×2bpp） | **够放下一次 WebDAV 下载的整帧**，这是关键 |
| app 分区 | 1.25 MB，当前占 986 KB（**77%**） | 余量 ~294 KB；http_client+TLS 约 +80~110 KB，够；再加 JPEG 解码要精算 |
| store 分区 | 8 槽 × 128 KB，整槽擦写 | 每写一张 = 一次 128 KB 擦除；这才是磨损来源 |
| 唤醒链路 | 定时唤醒 → `display_task` → 投 `UI_EV_CAROUSEL_NEXT` | WebDAV 取图应插在「投事件之前」，取不到就回退轮播 |
| 设置存储 | NVS，`moink_settings_t`（SSID 33 / 密码 65 字节） | 新增字段需给默认值，老设备读到 0 要能回退 |

## 3. 功能一：连接 WiFi（APSTA + 热点转发）

### 3.1 方案

```
手机 ──WiFi──> MoInk-XXXX (softAP 192.168.4.1)
                  │  NAPT（IP 转发 + 地址转换）
                  └──WiFi STA──> 家用路由器 ──> Internet
```

- `WIFI_MODE_APSTA`：热点照旧，同时以 STA 身份连路由器。
- `esp_netif_napt_enable(ap_netif)`：AP 侧客户端经设备访问外网（DHCP/DNS 由 AP netif 提供）。
- 信道：ESP-IDF 同一射频只能一个信道，**STA 连上后 AP 会跟到路由器所在信道**，
  原来「固定信道 6」的做法要改成「连上后按 STA 信道对齐」，否则热点会掉线重连。

### 3.2 交互设计（不破坏现有体验）

- 页面「设置 → 网络」新增：WiFi 名称 / 密码 / **连接** / 断开 / 当前状态（IP、信号）。
- 未配置或连接失败：**保持纯 AP 模式**，行为与今天完全一致（不因联网失败而影响本地使用）。
- 连接成功：页面设备信息显示 `STA IP`，并给一句「热点已可上网」提示。
- 支持「只用热点不联网」的开关（默认开 WiFi 连接，但失败静默回退）。

### 3.3 改动点（预估，不动代码）

| 文件 | 改动 |
|---|---|
| `src/netif_ap.c` | `WIFI_MODE_AP` → 由设置决定 AP / APSTA；加 STA 连接状态机与重连退避；信道跟随 |
| `src/settings.[ch]` | 新增 `sta_ssid/sta_pass/sta_enable/napt_enable`，NVS 新键，默认关闭 |
| `src/main.c` | `/api/net`（GET 状态 / POST 配置 / POST 连接测试）；`/api/info` 增 `sta_ip`、`rssi` |
| `page/index.html` | 网络设置区 + 状态徽标 |
| `sdkconfig.defaults` | 开 `CONFIG_LWIP_IP_FORWARD`、`CONFIG_LWIP_IPV4_NAPT` |

### 3.4 风险与坑

1. **NAPT 现在没开**：不改 sdkconfig 就调 `esp_netif_napt_enable()` 会直接返回错误。
   开转发会多占 lwIP 包缓冲（每个 pbuf 约 1.6 KB，实际增量需实测，估 +8~16 KB）。
2. **强制门户（captive portal）会失效**：今天手机连热点会自动弹配置页，是因为「无外网」触发探测。
   一旦热点能上网，探测通过 → **不再自动弹页**，用户得自己开 `192.168.4.1`。
   ⇒ 建议：保留 AP 侧 DNS 劫持对 `connectivitycheck.*` 的特殊处理（把探测域名照旧劫持到本机），
   这样既保弹页、又有外网。这条要做实验确认 iOS/Android 表现。
3. **功耗**：STA 常连会让睡眠电流上不去（WiFi 在深睡时本来断开，问题不大）；
   但空闲待机时若保持 APSTA，平均电流明显高于纯 AP。建议「无 STA 客户端 10 分钟后关 AP」或反过来。
4. **首次配网死锁**：用户把 WiFi 密码填错 → 连不上 → 但热点还在，可以改。这是安全的；
   只要保证「STA 失败绝不阻塞 AP」。
5. **密码明文存 NVS**：与今天 AP 密码同级别，属于可接受范围，但文档要写清。

## 4. 功能二：WebDAV 远程取图

### 4.1 取图路线：定案 A（服务器放 `.bin`）

> **v1 = 单个地址一张图；v2 = 远程图槽（一个目录 + 目录表，张数不限）。**
> 两者是同一模型的两种规模，v1 是 v2 在「只有 1 张」时的退化情形。完整模型见 **§4.9**。

| 路线 | 服务器上放什么 | 设备侧工作 | 额外 RAM | 结论 |
|---|---|---|---|---|
| **A（定案）** | 已算好的 `.bin`（16 B 帧头 + 2bpp 载荷，105,984 B） | 流式写入帧缓冲 → 校验 → 刷屏 | **0** | ★ 采用 |
| B | 原始 JPEG | 软件解码 + 缩放 + 四色量化 + Bayer | **约 +42 KB** | ✗ 否决，见 §4.1.1 |
| C | JPEG → 由 NAS 转 `.bin` | 同 A | 0 | ✓ 这不是独立路线，是 A 的「谁来生成」 |

**A 成立的前提已经现成**：`page/index.html` 本来就会导出 16 B 头 + CRC16 + 2bpp 的完整帧
（`hdr[0]=0xA5, hdr[1]=0x5A`），设备端不需要任何图像算法，画质与网页端**逐像素一致**。

自动化程度不需要靠设备端解决 —— 交给 NAS 上的一个定时脚本即可（见 §4.8）。

#### 4.1.1 为什么不做 JPEG（2026-11-05 核实）

先把硬件事实摆清：**ESP32-C3 没有硬件 JPEG 编解码**。
`soc/esp32c3/include/soc/soc_caps.h` 里没有 `SOC_JPEG*`（那三项只在 `esp32p4` 里），
`components/esp_rom/esp32c3/ld/esp32c3.rom.ld` 里也没有任何 jpeg 符号。
所以只能软件解码（tjpgd 系），内存必须先算。

| 项 | 字节 | 说明 |
|---|---|---|
| C3 DRAM 总量 | 409,600 | 无 PSRAM |
| 静态占用 | 39,692 | 现有编译输出（RAM 39,692 / Flash 1,009,216） |
| 开机 + WiFi 起来后的 free heap | 约 120,000~150,000 | **估算**（WiFi 栈 + lwIP + httpd），待接设备读 `/api/info` 的 `heap` 实测 |
| `frame_init()` 已 malloc | 120,000 | `EPD_MAX_BUF_LEN` |
| **剩余** | **约 0~30,000** | — |
| tjpgd 工作区 | 约 3,100 | Huffman / 量化表 / 状态 |
| MCU 行缓冲（768 宽 × 16 行 × RGB888） | 36,864 | **4:2:0 上采样必须整 MCU 行**，是 tjpgd 的硬设计，不是实现偷懒 |
| 垂直缩放行累加器 | 2,304 | 768 × 3 |
| **解码峰值额外需求** | **约 42,000** | — |

**结论：拿不出来。** 硬凑只有三条路，三条都不可接受：

1. 帧缓冲 120 KB → 106 KB（放弃 800×600 几何）：省 14 KB，仍差 28 KB。
2. 砍 WiFi 缓冲（`STATIC_RX_BUFFER_NUM` 10→4、`DYNAMIC_RX_BUFFER_NUM` 32→16）：省约 30 KB，
   但下载变慢、丢包重传变多，且这几项是 WiFi 栈内部行为，风险不可控。
3. 用 1/2 DCT 缩放解码（MCU 行缓冲减半到 18 KB）：解出 384×276 再放大 2 倍，画质直接崩。

即便勉强跑起来，还有四个**设备端解决不了**的问题：

- **缩放只能最近邻**：4 色 + Bayer 8×8 网点对缩放伪影极敏感，边缘阶梯会被量化放大成色带。
  `.bin` 方案下缩放/裁切在服务器端做，可以用任意高质量算法（面积平均 / Lanczos）。
- **不支持 progressive JPEG**：tjpgd 只吃 baseline，手机和微信导出的图里 progressive 很常见。
- **EXIF 旋转要自己写**：手机竖拍照片 `Orientation=6`，不处理就是躺着的。
- **CMYK / 16-bit / 异常色域**：全都要自己兜底。

一句话：不是「能不能跑」，而是「跑出来能不能看」。**定案 A。**

### 4.2 时序：唤醒后先试网络，失败回退本地图槽

**已定策略（用户 2026-11-05）：同步频率复用现有 `wake_s`，不另设间隔。
配了远程地址就先走网络，没配或失败就走本地图槽。**

```
定时唤醒(timer)  —— 复用 wake_s，与现在同一条路径
   ├─ 未配置远程（或开关关） → 现有逻辑：显示下一个本地槽 → 睡
   └─ 已配置远程
        └─ WiFi STA 连接（2~5 s，失败 → 回退本地槽，不空屏）
             └─ GET <远程根>/moink/moink.mf（≤4 KB，见 §4.9）
                  ├─ 目标行 CRC32 == 上次刷的 → 不下载、不刷屏，直接睡（只花 1~2 KB 流量）
                  ├─ 需要更新 → GET <名称>.bin → 校验魔数/几何/CRC16 → 写帧缓冲 → 刷屏 → 睡
                  └─ 任何失败（超时/404/格式错/校验错）→ **回退本地槽**，保留原画面
   └─ 断开 WiFi → 深睡
```

关键点：
- **直接写 `frame` 缓冲，不落 flash** —— 用户已定「刷完不存图」，所以**不走 `store_save_frame()`**，
  内存里刷完即弃。flash 磨损问题从根上消失（`store` 只用于本地图槽，与网络图无关）。
- **失败一律不刷屏**：墨水屏断电不丢画面，所以断网/弱网时屏幕保持原图，比刷成白屏安全得多。
- 回退顺序是「网络失败 → 本地图槽」，保证每次唤醒都有内容变化，不会卡在同一张。
- 全程硬超时 30 s，超时就睡，防止弱网把电池耗干。

### 4.3 去重（省钱省电的关键）

主判据用 **manifest 里的 CRC32**（§4.9），不依赖服务器支持 ETag —— 因为「普通 HTTP 静态目录」
和「NAS 上的文件」不一定给一致的 ETag，而 CRC32 是生成端自己写的，三端统一。

- 远程图槽模式：比对 `moink.mf` 里目标行的 CRC32，一致就**连图都不下载**。
- 单 URL 模式（退化情形）：服务器给 `ETag`/`Last-Modified` 就带 `If-None-Match`；
  不给就退化为「下载后比 CRC32」。
- 无论哪种，**判重失败不会刷错图**：最终都以 `.bin` 内的 CRC16 为准。

### 4.4 协议只需要 HTTP GET（WebDAV 只是其中一种）

用户澄清「WebDAV 只是个例子」，那么正确的抽象是：**设备端只认「一个 HTTP(S) 上的 `.bin` 地址」**。
WebDAV 的取文件本来就是普通 `GET`，所以同一套代码覆盖：

| 放 .bin 的地方 | 设备端要改什么 |
|---|---|
| WebDAV（群晖 / 飞牛 / 坚果云 / Alist） | 无，`GET` + Basic 认证 |
| 普通 HTTP 静态文件（NAS 共享 / Nginx / 对象存储） | 无，`GET` |
| GitHub raw / 任意 CDN | 无，`GET` |

所以**不写 WebDAV 专用客户端**，只写一个「带可选 Basic 认证的 HTTP GET」：

- 必需：`GET` + `HTTP_AUTH_TYPE_BASIC` + 流式读回调 + 超时。
- 可选：`HEAD`（或 `If-None-Match`）判 ETag；`Range` 不做。
- **不做 PROPFIND**：路径写死即可。想「读文件夹里最新一张」属于 v3，且 XML 解析在 C3 上是纯负担。
- ESP-IDF 自带 `esp_http_client` 就够，**不必引第三方库**。

这一条把实现量砍掉一半：不用懂 WebDAV，只用懂 HTTP。

### 4.5 flash 磨损（已定：不存）

用户决策：**刷完不存图**。所以网络来的图直接进帧缓冲、刷完即弃，`store` 分区完全不被触碰。

顺带把量级记下来，免得以后再纠结：8 槽轮换、每天 4 次 ≈ 183 次擦写/槽/年，
NOR 典型 10 万次寿命 ⇒ 要 500 年才到寿命。所以「省 flash」的真实收益是**省电和省时间**，
不是救命 —— 但既然不存正好也更省，就不存。

### 4.6 触发方式

| 触发 | 说明 |
|---|---|
| 定时唤醒（主，已定） | **复用现有 `wake_s`，不新增间隔**。唤醒后：有 URL 先取网络图，失败/未配置走本地槽 |

### 4.7 安全

- 只支持 **HTTP 明文** 或 **HTTPS（跳过证书校验）** 两档起步；要严格校验就得带 CA，
  会多吃 30~40 KB flash 和握手 RAM，v1 不做。
- 强烈建议 URL 里带一段随机路径做「弱口令」（TRMNL / InkTime 都这么干），
  比在公网暴露 WebDAV 目录安全。
- 密码进 NVS 明文，文档写明；公网请走 HTTPS + 反向代理鉴权。

### 4.8 谁来生成 `.bin`（设备端零算法的另一半）

既然定了放 `.bin`，「图从哪来」就变成 PC/NAS 侧的事。三种生成方式，可以并存：

| 方式 | 怎么做 | 适合 |
|---|---|---|
| **网页手动导出（已有）** | `page/index.html` 选图 → 裁切 → 导出 `.bin` → 丢进服务器目录 | 偶尔换图 |
| **NAS 定时脚本（推荐 P3）** | 飞牛 NAS 上 Python 脚本：读照片目录/抓网络图 → `Pillow` 缩放裁切 → 量化成 2bpp → 加 16 B 头 → 写进 HTTP 目录 | 每天自动换 |
| 云端生成 | 服务器渲染（TRMNL 路线） | 要做内容服务时 |

**关键**：NAS 侧的量化必须和我们固件里的完全一致，否则颜色会偏。做法是**复用页面里的实现**：
把 `page/index.html` 里的 `BAYER8` 表 + 量化函数抽成一个独立 Python 模块（一一对应、加断言），
而不是另写一套近似算法。这样三端（网页 / NAS / 固件验证）逐像素对齐。

`Pillow` 侧只需要四件事，都是标准调用：
```python
im = Image.open(p); im = ImageOps.exif_transpose(im)   # ① 手机竖拍自动转正
im = ImageOps.fit(im, (768, 552), Image.LANCZOS)       # ② 任意尺寸等比裁切缩放
# ③ 转 Lab → Bayer 8×8 阈值量化到 4 色（复用页面算法）
# ④ 打包 16 B 头 + CRC16 + 2bpp 载荷
```

### 4.9 远程图槽模型（v2 的核心）

用户的模型是：**把本地 8 槽的「图槽」概念平移到远程**，不是「一个固定 URL」。
远程可以不限量存图，设备照常轮播、照常上传，只是仓库从 `store` 分区换成远程目录。

这要求设备能知道三件事：**远程有几张、当前该显示第几张、这张的文件名是什么**。
所以远程目录必须有**一个目录表**（manifest）—— 这是本地 `store` 里由固件维护、远程必须由生成方维护的那部分信息。

#### 目录结构

```
<远程根>/moink/
    moink.mf        # 目录表（≤4 KB）
    0001.bin        # 与本地图槽完全相同的格式（16 B 头 + 2bpp）
    0002.bin
    ...
```

#### `moink.mf` 格式（纯文本，逐行，便于流式解析）

```
MOINKMF1
count 12
cur 5
0001.bin 3fa2c1d0
0002.bin 88be12aa
...
```

| 行 | 含义 |
|---|---|
| `MOINKMF1` | 魔数 + 版本，防呆 |
| `count N` | 总张数 |
| `cur K` | 服务端指定要显示第 K 张（0 起）。**`cur -1` = 交给设备自增** |
| `名称 CRC32` | 每一项 8 位十六进制 CRC32，用于「没变就跳过下载」 |

**显式不做的两件事**：
- **不做 PROPFIND / 不列目录**：dev 只读 manifest，避免 XML 解析（C3 上是纯负担），也让非 WebDAV 的普通 HTTP 目录一样能用。
- **不读图片元信息**：宽高和 CRC16 都在 `.bin` 里，manifest 不重复。

#### 设备端轮播逻辑（NVS 存 `r_slot`、`r_crc`）

```
GET moink.mf（≤4 KB，超限即拒）
  ├─ 解析出 count、cur、目标行（第 target 行）
  ├─ target = (cur >= 0) ? cur : (r_slot + 1) % count      ← 服务端可指定，也可交给设备自增
  ├─ 若 manifest[target].crc == r_crc 且 target == r_slot  → 跳过，不下载、不刷屏、直接睡
  └─ 否则 GET <name> → 校验魔数/几何/CRC16 → 写帧缓冲 → 刷屏 → 更新 r_slot / r_crc
```

**两个场景一套逻辑**：
- **相册模式**：`cur -1`，设备每次唤醒换下一张 —— 就是现在 8 槽轮播的远程版。
- **内容模式**（你要的日历/日程）：服务端每次重写 manifest 并指向 `cur 0`，设备下次唤醒就显示新内容。
  服务端甚至可以不换文件名，只换内容 + CRC32。

#### 为什么 manifest 里要带 CRC32

不给 CRC32 的话，设备每次唤醒都要下载 106 KB 才能知道图变没变；
给了 CRC32，服务器没更新时**整个唤醒过程只传 1~2 KB 文本**，直接睡 —— 这是省电的关键。

### 4.10 上传到远程图槽（页面上传 → 远程）

现有链路是「页面 POST `/api/frame` → 设备收满整帧 → 校验 CRC → `store_save_frame()`」。
**图在 `s_fb` 里本来就是完整的**，所以「存到远程」只是把最后一步从「写 flash」换成「PUT 出去」，
**额外内存 ≈ 0**（HTTP 客户端缓冲 4 KB + socket）。

```
页面 → POST /api/frame?save=remote （body 与现在完全一样：16B 头 + 2bpp + 可选缩略图）
   └─ 设备收满 s_fb + 校验 CRC（现有逻辑不变）
        └─ PUT <远程根>/moink/<时间戳>.bin（Content-Length = 16 + 载荷长 + 缩略）
             ├─ 2xx → 立即用内存里的帧刷屏（不写本地槽）
             └─ 失败 → 返回 502，页面提示；帧仍在内存里，可选择「改存本地」
```

#### 一个必须避开的坑：不要让浏览器直接传 WebDAV

直觉上「页面直接 fetch PUT 到 WebDAV」最省设备资源，但实际走不通：

- 设备页面 origin 是 `http://192.168.4.1`，目标是另一台主机的 WebDAV ⇒ **跨域**；
- PUT + `Authorization` 头会触发 **OPTIONS 预检**；
- 而 nginx-dav / 飞牛 / 群晖的 WebDAV **默认都不返回 CORS 头**，预检失败，请求被浏览器拦掉。

要绕过就得在 NAS 上配 CORS 头（还得放行 `PUT`、`Authorization`），既麻烦又把「设备零负担」换成「NAS 配置负担」。

**所以上传走设备转发**：设备本来就要收这张图（要立刻刷屏），顺手 PUT 出去，不额外增加流量或内存。

### 4.11 远程图槽与本地图槽的关系

| 场景 | 行为 |
|---|---|
| 未配置远程地址 | 完全走现有逻辑，本地 8 槽轮播，行为不变 |
| 配了远程、网络正常 | 显示远程图槽；**不写本地槽**（按你的决定） |
| 配了远程、连不上/超时/校验失败 | **回退本地槽**（继续本地轮播），保证每次唤醒画面都有变化、不空屏 |
| 上传时选了「远程」但 PUT 失败 | 返回 502，图保留在内存并已刷屏，页面提示可改存本地 |

**不做远程/本地双写**：既然远程不限量，本地再存一份只是浪费一次 128 KB 整槽擦写。

## 5. 分阶段计划（建议）

| 阶段 | 内容 | 验收 | 预估 |
|---|---|---|---|
| **P0** | APSTA 连路由器（设置页 + `/api/net` + 状态显示 + 失败静默回退纯 AP） | 手机连热点仍能开 192.168.4.1；设备拿到 STA IP；断路由器能自动重连 | 小 |
| **P1** | 单张 `.bin` 最小闭环（GET + Basic + 写帧缓冲直刷 + 失败回退本地槽 + 30 s 超时） | 改服务器上的 .bin → 下次唤醒自动变；断网时画面不动 | 小 |
| **P2** | NAPT 让热点能上网（`LWIP_IP_FORWARD` + `IPV4_NAPT`）+ 强制门户兼容 | 手机连热点能上网，且仍能弹配置页 | 中 |
| **P3** | 生成端自动化（NAS 定时脚本：照片目录/网络图 → `.bin` → 重写 `moink.mf`） | 丢一张照片进 NAS 目录，设备下次唤醒自动换图 | 小（PC 侧，不占固件） |
| **P4** | **远程图槽**（manifest + 多图轮播 + 上传转发 PUT） | 远程放 12 张，设备按序轮播；页面选「存到远程」后远端多一张、本地 8 槽不变 | 中 |

**P3 从「设备端 JPEG 解码」改成「NAS 侧生成 `.bin`」** 是这次决策带来的最大简化：
设备端从 500+ 行解码/缩放/量化代码，变成 0 行；而 NAS 上 Python `Pillow` 十行搞定所有格式、
所有尺寸、所有 EXIF 旋转，画质还能用最好的重采样。

（原 P3「设备端 JPEG」已否决，理由见 §4.1.1。若将来换 C6/S3 带 PSRAM 的板子，可重新评估。）

## 7. 决策记录（2026-11-05 用户确认）

| # | 问题 | 决定 | 影响 |
|---|---|---|---|
| 1 | 热点转发是否必须 | **必须** | NAPT 进 P2，且是硬需求不是可选 |
| 2 | 服务器放 `.bin` 还是 JPEG | **`.bin`**（JPEG 经核实不可行，见 §4.1.1） | 设备端零图像算法，RAM 不增加 |
| 3 | 刷完是否存图库 | **不存** | 不调 `store_save_frame()`，flash 零写入 |
| 4 | 同步频率 | **复用 `wake_s`** | 不新增定时器，唤醒即有网走网、无网走本地槽 |
| 5 | 只支持 WebDAV？ | **不是**，任何 HTTP GET 都支持 | 不写 WebDAV 专用客户端，省一半实现量 |
| 6 | 「远程图槽」还是「单 URL」 | **远程图槽**：本地 8 槽的概念平移，张数不限，可上传到远程 | 需要目录表 `moink.mf`（§4.9）；设备端轮播逻辑复用现有 `cur`/`r_slot` 概念 |

### 仍需你确认的三件事

1. **生成端先做哪个**：① 网页手动导出（零开发，今天就能用）；② 一步到位写 NAS 定时脚本（飞牛上跑 Python，丢照片进目录自动换）。
2. **远程目录放在哪**：飞牛 NAS 的 WebDAV 目录？还是 NAS 上开个普通 HTTP 静态目录（更简单，连认证都不用）？
3. **`cur` 归谁管**：我建议 `cur -1 = 设备自增`（相册场景）+ `cur N = 服务端指定`（日历场景）**两种都支持**，
   默认给 `-1`。若你只想留一种，告诉我。
