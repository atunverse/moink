# 需求：设备联网（WiFi + 热点转发）与 WebDAV 远程取图

> 记录日期：2026-11-05　状态：**需求评估中，未动代码**
> 关联：FB-023（功能一）、FB-024（功能二）　参考项目见 §6
> 原则：本文只做可行性与路径分析；实施需另行确认方案后再动码。

---

## 1. 需求原文与我的解读

**功能一**：在现有「开机开热点」不变的前提下，增加「连接 WiFi」设置。连上路由器后设备能上网，
用户连它的热点也能上网 —— 不要在连接设备时把用户的手机断网。

**功能二**：基于功能一，定时唤醒后不从 flash 图槽取图，而是连 WiFi → 连 WebDAV → 读指定文件 → 刷到屏上。

这里有一处必须先分清，它决定工作量差一倍：

| 解读 | 含义 | 实现 | 工作量 |
|---|---|---|---|
| A. 手机连设备热点，设备只是「自己也联网了」 | 手机仍无外网，只是设备能拉图 | 仅 APSTA 共存 | 小 |
| **B. 手机连设备热点就能上网（设备当二级路由）** | 设备把 AP 侧流量 NAT 到 STA 侧 | APSTA + **NAPT**（`esp_netif_napt_enable`） | 中 |

按你的描述（「通过连接它的热点来连接网络，不会造成在连接设备的时候用户就断网了」），
我理解你要的是 **B**。技术上成立：ESP-IDF 提供官方 NAPT 接口，ESP32-C3 支持。
但当前工程 `sdkconfig` 里 `CONFIG_LWIP_IP_FORWARD` 是**关闭**的，必须打开才能做转发（§3.4）。

## 2. 现状与硬约束（决定了方案边界）

| 项 | 现状 | 对方案的限制 |
|---|---|---|
| 芯片 | ESP32-C3 SUPERMINI，**无 PSRAM**，约 320 KB 可用堆 | 不能同时握两块 106 KB 帧缓冲；不能整帧 RGB 解码 |
| WiFi 模式 | `netif_ap.c` 里 `WIFI_MODE_AP` + 固定信道 6 | 改 APSTA 后 AP 信道必须跟随路由器信道（同一射频） |
| 静态 RAM | 39,692 B（R1.3.4） | 加 WiFi STA + TLS + NAPT 后要实测余量 |
| 帧缓冲 | `frame_init()` 一次 malloc ≈ 106 KB（768×552×2bpp） | **够放下一次 WebDAV 下载的整帧**，这是关键 |
| app 分区 | 1.25 MB，当前占 986 KB（**77%**） | 余量 ~294 KB；http_client+TLS 约 +80~110 KB，够；再加 JPEG 解码要精算 |
| store 分区 | 8 槽 × 128 KB，整槽擦写 | 每写一张 = 一次 128 KB 擦除；这才是磨损来源 |
| 唤醒链路 | 定时唤醒 → `display_task` → 投 `UI_EV_CAROUSEL_NEXT` | WebDAV 取图应插在「投事件之前」，取不到就回退轮播 |
| 设置存储 | NVS，`moink_settings_t`（SSID 33 / 密码 65 字节） | 新增字段需给默认值，老设备读到 0 要能回退 |

## 3. 功能一：连接 WiFi（APSTA + 热点转发）

### 3.1 方案

```
手机 ──WiFi──> MoInk-XXXX (softAP 192.168.4.1)
                  │  NAPT（IP 转发 + 地址转换）
                  └──WiFi STA──> 家用路由器 ──> Internet
```

- `WIFI_MODE_APSTA`：热点照旧，同时以 STA 身份连路由器。
- `esp_netif_napt_enable(ap_netif)`：AP 侧客户端经设备访问外网（DHCP/DNS 由 AP netif 提供）。
- 信道：ESP-IDF 同一射频只能一个信道，**STA 连上后 AP 会跟到路由器所在信道**，
  原来「固定信道 6」的做法要改成「连上后按 STA 信道对齐」，否则热点会掉线重连。

### 3.2 交互设计（不破坏现有体验）

- 页面「设置 → 网络」新增：WiFi 名称 / 密码 / **连接** / 断开 / 当前状态（IP、信号）。
- 未配置或连接失败：**保持纯 AP 模式**，行为与今天完全一致（不因联网失败而影响本地使用）。
- 连接成功：页面设备信息显示 `STA IP`，并给一句「热点已可上网」提示。
- 支持「只用热点不联网」的开关（默认开 WiFi 连接，但失败静默回退）。

### 3.3 改动点（预估，不动代码）

| 文件 | 改动 |
|---|---|
| `src/netif_ap.c` | `WIFI_MODE_AP` → 由设置决定 AP / APSTA；加 STA 连接状态机与重连退避；信道跟随 |
| `src/settings.[ch]` | 新增 `sta_ssid/sta_pass/sta_enable/napt_enable`，NVS 新键，默认关闭 |
| `src/main.c` | `/api/net`（GET 状态 / POST 配置 / POST 连接测试）；`/api/info` 增 `sta_ip`、`rssi` |
| `page/index.html` | 网络设置区 + 状态徽标 |
| `sdkconfig.defaults` | 开 `CONFIG_LWIP_IP_FORWARD`、`CONFIG_LWIP_IPV4_NAPT` |

### 3.4 风险与坑

1. **NAPT 现在没开**：不改 sdkconfig 就调 `esp_netif_napt_enable()` 会直接返回错误。
   开转发会多占 lwIP 包缓冲（每个 pbuf 约 1.6 KB，实际增量需实测，估 +8~16 KB）。
2. **强制门户（captive portal）会失效**：今天手机连热点会自动弹配置页，是因为「无外网」触发探测。
   一旦热点能上网，探测通过 → **不再自动弹页**，用户得自己开 `192.168.4.1`。
   ⇒ 建议：保留 AP 侧 DNS 劫持对 `connectivitycheck.*` 的特殊处理（把探测域名照旧劫持到本机），
   这样既保弹页、又有外网。这条要做实验确认 iOS/Android 表现。
3. **功耗**：STA 常连会让睡眠电流上不去（WiFi 在深睡时本来断开，问题不大）；
   但空闲待机时若保持 APSTA，平均电流明显高于纯 AP。建议「无 STA 客户端 10 分钟后关 AP」或反过来。
4. **首次配网死锁**：用户把 WiFi 密码填错 → 连不上 → 但热点还在，可以改。这是安全的；
   只要保证「STA 失败绝不阻塞 AP」。
5. **密码明文存 NVS**：与今天 AP 密码同级别，属于可接受范围，但文档要写清。

## 4. 功能二：WebDAV 远程取图

### 4.1 三条取图路线

| 路线 | 服务器上放什么 | 设备侧工作 | RAM | 我给的评价 |
|---|---|---|---|---|
| **A（推荐 v1）** | 我已经算好的 `.bin`（16 B 帧头 + 2bpp 载荷，106 KB） | 直接流式写入帧缓冲 → 校验 → 刷屏 | 0 额外 | ★ 最快落地，画质与网页端**逐像素一致** |
| **B（推荐 v2）** | 普通 JPEG | 流式解码（逐行）→ 逐行四色量化 + Bayer → 写帧缓冲 | 约 +8~12 KB | 可行，见 §4.3；C3 上 CPU 约 1~3 s |
| C | JPEG，由常开服务（NAS/树莓派）转 `.bin` | 同 A | 0 | 最省设备算力，但多一台常开机器 |

**为什么 A 是 v1**：本机已经把「四色量化 + Bayer 网点 + 帧头打包」全放在页面里了，
`page/index.html` 能直接导出可用的帧；把它传到 WebDAV 即可，设备端不需要任何图像算法，
风险最低，而且不碰算法冻结区。

**为什么 B 现在也算可行**（这条是这次调研的收获）：我们的量化是 **Bayer 8×8 有序网点**，
逐像素、无误差扩散、无反馈 ⇒ **逐行解码 + 逐行量化，与整帧量化的结果完全等价**。
所以不需要 847 KB 的 RGB 整帧缓冲，用「流式逐行 JPEG 解码器」即可：
`embedblocks/jpeg-roi-decoder`（基于 tjpgd，行回调、零堆分配，声称支持 C3）。

### 4.2 v1 时序（醒来一次做完就睡）

```
定时唤醒(timer)
   └─ WiFi STA 连接（2~5 s，失败→回退轮播，最长等 8 s）
        └─ HTTP HEAD/GET 目标 URL（Basic 认证；对比 ETag/Last-Modified）
             ├─ 未变化 → 直接睡（不刷屏、不写 flash）
             └─ 变化 → 流式读入 frame 缓冲（跳过/校验 16 B 头、几何、CRC16）
                   ├─ 可选：写入 store 槽（默认关，见 §4.5）
                   └─ epd_display_2bpp() 刷屏（5~15 s）
   └─ 断开 WiFi → 深睡
```

关键点：
- **直接写 `frame` 缓冲，不落 flash** —— 满足你「别磨 flash」的诉求。
- 下载失败/校验失败 → **一律不刷屏**，保持屏幕上原来的图（电子墨水屏断电不丢画面，天然安全）。
- 全程给一个硬超时（建议 30 s），超时就睡，防止弱网把电池耗干。

### 4.3 去重（省钱省电的关键）

- 第一次成功下载后把 `ETag`（或 `Last-Modified` + 内容长度）存 NVS；
  以后每次先 HEAD，一样就跳过。NAS 上的 WebDAV 一般都给 ETag。
- 没有 ETag 的服务器：退化为「下载后算 CRC32 比对上次」，多花流量但不刷屏。

### 4.4 WebDAV 到底要多少协议

只需要三件事：`GET`（带 Basic 认证）、`HEAD`（可选）、`PUT`（可选，页面直接推图时用）。
- **不需要 PROPFIND**：目标文件路径写死即可。想「读文件夹里最新一张」才需要 PROPFIND + XML 解析，
  建议放到 v3，而且解析 XML 在 C3 上是纯负担。
- ESP-IDF 自带 `esp_http_client` 就够：支持 `HTTP_AUTH_TYPE_BASIC`、流式读、`HTTP_METHOD_HEAD`，
  也有 `HTTP_METHOD_PROPFIND` 备用。**不必引第三方库**。

### 4.5 flash 磨损到底有多大（先算清再决定）

- 8 槽轮换，每天 4 次刷图 = 1460 次/年 ÷ 8 槽 ≈ **183 次擦写/槽/年**。
- NOR flash 典型擦写寿命 10 万次 ⇒ 按这个频率要 **500 年**才到寿命。
- 真正的代价不是寿命，是**每次开机多一次 128 KB 整槽擦写**（约几十 ms + 峰值电流）和
  「为了存一张图而写 flash」这件事本身的别扭。
- 结论：**默认不写槽**（纯显示），用户勾「保存到图库」才写；这样既省电也彻底不磨。

### 4.6 触发方式

| 触发 | 说明 |
|---|---|
| 定时唤醒（主） | 复用现有 `wake_s`；新增「唤醒后先同步 WebDAV」开关，取不到图退回轮播 |
| 按键长按（备） | 已用长按关机，建议改为「双击后长按」或页面按钮「立即同步」 |
| 页面「立即同步」 | `POST /api/webdav/sync`，人在旁边时用，方便调试 |

### 4.7 安全

- 只支持 **HTTP 明文** 或 **HTTPS（跳过证书校验）** 两档起步；要严格校验就得带 CA，
  会多吃 30~40 KB flash 和握手 RAM，v1 不做。
- 强烈建议 URL 里带一段随机路径做「弱口令」（TRMNL / InkTime 都这么干），
  比在公网暴露 WebDAV 目录安全。
- 密码进 NVS 明文，文档写明；公网请走 HTTPS + 反向代理鉴权。

## 5. 分阶段计划（建议）

| 阶段 | 内容 | 验收 | 预估 |
|---|---|---|---|
| **P0** | 只做 APSTA 能连路由器（不做 NAPT、不做取图），设置页 + `/api/net` + 状态显示 | 手机连热点仍能开 192.168.4.1；设备拿到 STA IP；断开路由器能自动重连 | 小 |
| **P1** | WebDAV v1（.bin 直刷 + ETag 去重 + 失败回退 + 30 s 超时） | 改 NAS 上的 .bin → 下次唤醒自动变；断网时画面不动、不误刷 | 中 |
| **P2** | NAPT 让热点能上网 + 强制门户兼容 | 手机连热点能刷网页，且仍能弹出配置页 | 中 |
| **P3** | WebDAV v2（JPEG 流式解码 + 四色量化） | 直接丢 JPEG 进 WebDAV 也能出图，画质与网页端一致 | 中偏大 |

我建议 **P0 → P1 先做**，因为 P0 单独就有价值（用户可以手机和电脑同网访问设备），
P2 的强制门户兼容是「锦上添花但容易踩坑」的一项，放后面。

## 7. 需要你定的几件事

1. **热点转发**是不是必须（P2）？如果只是「设备自己联网、手机用家里 WiFi 访问设备」，P0 就够。
2. WebDAV 上放 **`.bin`（我做好的帧）** 还是 **原始 JPEG**？前者稳、后者方便。
3. 刷完要不要**存进图库**（8 槽）？我倾向默认不存。
4. 定时同步频率（跟现有定时唤醒同一个 `wake_s`，还是单独一个 WebDAV 间隔）。
5. 只支持 **WebDAV**，还是顺便支持普通 HTTP 直链（一行代码的差别，兼容性更好）。
