# 评估 · 图片轮播功能可行性（FB-017）

> 本文档为**技术可行性评估**，非实施方案。结论：✅ 技术可行，核心成本在「分区表变更 + 唤醒脚语义 + 存储管理」，渲染/休眠/唤醒框架可大量复用。
> 参考的优秀实现：`aitjcize/esp32-photoframe`（核心范式）、`sephiroth74/esp32-photo-frame`（离线本地循环）、`jwchen119/EPF`（短按唤醒 + 处理下放服务端）。

---

## 0. 结论速览

| 维度 | 结论 |
|---|---|
| 整体可行性 | ✅ 可行，业界已有成熟低功耗范式可直接对标 |
| 可复用的现有能力 | 渲染管线（2bpp packed）、深度休眠 + GPIO/定时唤醒、帧上传协议、NVS 设置框架 |
| 必须新增的核心能力 | ① 跨唤醒持久化存储分区（LittleFS）② 轮播端点与唤醒调度逻辑 ③ 控制页管理 UI |
| 最大风险 | ★★ 分区表变更（4 MB 已填满，重分需整包重刷）；★ 手动唤醒脚语义；随机模式跨重启确定性 |
| 推荐版本 | 功能新增 → **R1.3.0**（帧契约 `api` 不变，仍 2） |
| 功耗预期 | 单图/唤醒范式下，每次仅一次全刷 + 长眠，续航与现状（数月级）同量级 |

## 1. 需求拆解

| # | 需求 | 类型 | 落地形态 |
|---|---|---|---|
| 1 | 开启 / 关闭轮播 | 开关 | NVS 布尔 `carousel_on` |

## 2. 现有基础（可复用 vs 缺口）

### 2.1 ✅ 可直接复用

- **渲染管线**：控制页 `renderComposite` 已把任意图处理成 **2bpp packed 帧**（768×552 → 105,984 B ≈ **103 KB/张**）。设备端 `frame.c` 只需把缓冲推到 EPD，**无需在固件里重算色彩/抖动**。轮播复用同一产物即可。
- **休眠/唤醒框架**（`src/power.c`）：已实现
  - `power_enter_deep_sleep()`：`esp_sleep_enable_gpio_wakeup_on_hp_periph_powerdown(EPD_PIN_WAKE_BTN, LOW)` + `esp_sleep_enable_timer_wakeup(wake_s)`。
  - **手动唤醒按钮已存在** —— 即 `EPD_PIN_WAKE_BTN`（GPIO5，低电平唤醒），与长按 5 s 恢复出厂共用一支物理键。
- **帧上传协议**：`/api/frame` 已存在（当前只写 RAM）。可扩展为「写存储」。
- **设置框架**：`settings.c` 的 NVS 读写可承载开关/模式/间隔/索引。

### 2.2 ❌ 当前缺口

- **无跨唤醒持久化**：`frame_upload_handler` 只把帧放进 RAM `s_fb` 并唤醒显示任务；**深度睡眠后 RAM 清零**，屏幕靠 e-ink 双稳余辉保留旧图。轮播必须新增「掉电/休眠后仍在」的存储。
- **无存储分区**：见 §5 R1，`partitions.csv` 已精确填满 4 MB，没有给图片留空间。
- **无轮播调度**：开机路径只渲染「当前这一帧」，没有「下一张」概念、没有顺序/随机选择逻辑。

## 3. 参考的优秀实现（外部）

### 3.1 `aitjcize/esp32-photoframe` ⭐ 核心参考
- **电源范式**：Deep Sleep 默认开启，**唤醒来源 = BOOT/KEY 按钮 或 auto-rotate 定时器**；Web 界面仅在 awake 时可达；睡眠 ~10 µA，续航数月。
- **图像来源**：SD 卡旋转 / URL 拉取；**measured palette（实测色板）+ Floyd-Steinberg 抖动**。
- **Web 管理**：拖拽上传、画廊视图、实时电量、Settings 里配旋转间隔与模式。
- **启示**：**one-image-per-wake（每次唤醒只显示一张）→ 回到休眠** 是低功耗标准范式；处理在上传侧完成，设备只 blit。

### 3.2 `sephiroth74/esp32-photo-frame`
- **Offline Mode**：图片存 SD 卡本地循环；`config.json` **零重编译配置**（间隔/来源全在文件里）；Night Mode 夜间暂停省电。
- **启示**：离线优先、配置走数据文件而非硬编码。

### 3.3 `jwchen119/EPF`
- **交互**：deep sleep 中**短按设置键唤醒重启流程**，长按 ~5 s 进入设置模式（与本项目 GPIO5 语义高度同构）。
- **架构**：图像处理/量化全在伺服端，设备只渲染，睡眠 ~16 µA。
- **启示**：处理下放页面/伺服端，固件保持「轻显示」。

### 3.4 共识范式（用于 §4 设计）
> **单图/唤醒 + 本地存储 + 上传侧处理 + Web 管理 UI** 是 ESP32 e-ink 相框的事实标准。本项目已有「上传侧处理（renderComposite）」和「深度休眠 + 双唤醒源」，缺口仅是「本地存储」与「调度逻辑」。

## 4. 推荐架构

### 4.1 存储（新增 LittleFS data 分区）
- 存 **2bpp packed 帧**（103 KB/张）+ **meta**（列表顺序、播放模式、间隔）。
- 空间估算（4 MB 重分后）：`web` 960 KB → 512 KB（页面仅 143 KB，余量充足）省 ~448 KB；两个 `ota` 槽 1.5 MB → 1.2 MB（app 实测 <1 MB，余量充足）各省 0.3 MB → 合计释放 **~1.05 MB ≈ 10 张**。可按需再压缩。

### 4.2 端点（新增，不碰 `/api/upload` 升级入口）
| 端点 | 作用 |
|---|---|
| `POST /api/carousel/add` | 接收打包后的 2bpp blob，写入 LittleFS，返回 id |
| `GET  /api/carousel/list` | 列表 + 顺序 + 模式 + 间隔 |
| `POST /api/carousel/del` | 删除指定 id |
| `POST /api/carousel/cfg` | 开关 / 模式 / 间隔 / 顺序 |
| `POST /api/carousel/advance` | 手动切下一张并立即刷新 |

### 4.3 唤醒轮播逻辑（挂在 `main.c` 开机路径）
```
boot → esp_sleep_get_wakeup_causes()
  ├─ TIMER 或 GPIO(手动) 且 carousel_on:
  │     idx = next(mode)          // seq: (idx+1)%N ; rand: PRNG(种子)
  │     read LittleFS frame[idx] → s_fb
  │     epd 渲染
  │     power_enter_deep_sleep()  // 定时器 = 间隔
  └─ 否则: 维持现状（渲染已存帧 / 等待）
```
- `idx` 持久化：NVS `u8`（或 `RTC_DATA_ATTR` 省 NVS 擦写）。
- 随机模式跨重启：用 RTC 慢速内存或存储 PRNG 状态，避免每次都从头。

### 4.4 控制页 UI（新增「轮播」标签页）
开关 · 间隔 · 模式(顺序/随机) · 多图上传 · 列表(排序/删除/预览) · 立即下一张。

## 5. 关键技术要点与风险（★）

- **R1 ★★ 分区表变更（最大成本）**：4 MB 已填满（`web` 结束于 `0x400000`）。必须重分，且**首次需整包重刷**（含新分区表）；OTA 期间新旧分区表不一致需由 FlashKit 写新表解决。建议 `ota` 缩到 1.2 MB + `web` 缩到 512 KB，凑 ~1 MB LittleFS。
- **R2 ★ 手动唤醒脚语义**：`EPD_PIN_WAKE_BTN`(GPIO5) 已用于 deep-sleep 唤醒 + 长按 5 s 恢复出厂。短按唤醒可直接复用，但需确认短按**不会误触**恢复出厂（恢复出厂是长按 5 s，一般互斥）；需在 boot 区分 `wakeup_cause` 与按键时长。
- **R3 ★ 轮播语义（需与用户确认）**：**单图/唤醒**（推荐，省电、业界标准，每次唤醒显示下一张后休眠）vs **一次唤醒连播多张**（需保持唤醒 + 多次全刷，4 色屏每次必全刷会闪、功耗高）。语义不同，实现差异大。
- **R4 ★ 存储上限与磨损**：LittleFS 有擦写寿命；须限制 N 张 / 总大小，上传前校验尺寸，删除即回收。
- **R5 ★ 升级重置交互**：`settings_reset_for_upgrade()` 当前清 `panel/hflip/a1_mode/wifi_pwr/sleep_s/wake_s`。轮播配置（开关/模式/间隔）应**保留**还是随强制重置清除？图片在 LittleFS（与 NVS 分离，升级不丢图），但开关被重置 → 建议轮播配置加入「保留」名单，否则每次升级后轮播静默关闭。
- **R6 ★ 随机模式跨重启确定性**：用 `RTC_DATA_ATTR` 存 idx/种子，或持久化 PRNG 状态。
- **R7 全刷闪烁**：4 色屏每次切换必全刷（驱动无局刷），轮播天然闪；可接受，但 UI 应提示。
- **R8 版本**：功能新增 → R1.3.0（`api` 仍 2，帧契约不变）。
- **R9 内存**：复用 `s_fb`（120 KB）读 LittleFS 即渲，无需新增大缓冲。
- **R10 电池**：`power_battery_mv()` 已监测，低电可暂停自动唤醒省电。

## 6. 实施分期建议

- **P1（核心，纯固件 + 存储）**：分区重分 + LittleFS + `/api/carousel/add|list|del` + 唤醒轮播（先做顺序）。真机验证「上传 N 张 → 定时轮换」。
- **P2（体验）**：模式(随机)/间隔/开关 UI + `advance` 手动 + 升级保留配置。
- **P3（打磨）**：列表排序/预览/缩略图、夜间暂停、图损坏跳过等异常兜底。

### 8.2 延寿调研结论（详见 `docs/调研-内置Flash延寿方案.md`）

- **选型反转**：评估时建议 LittleFS，调研后改为**裸分区 + 整槽轮转** —— 轮播帧是「定长大对象、写一次读多次」，整槽轮转的写放大 **WAF ≈ 1**（每张图只消耗一次整槽擦除）；LittleFS/FATFS 的元数据提交与固定头部反而是擦写热点，其优势（变长小文件、断电一致性）对本场景无意义。
- **寿命测算**：8 槽摊平后 10 万次/槽擦写上限 ⇒ **80 万次换图**（每天换 10 张 ≈ 219 年）—— Flash 寿命不是瓶颈；真正要防的是「高频改写 NVS 键」与「固定地址元数据头」（裸槽方案天然无后者）。
- **写入顺序预设（第二部分实现）**：先写整槽帧 → 读回校验 → 最后 NVS 提交游标 —— 任何一步掉电都不会出现「游标指向半张图」。
- 配套约束：游标等高频元数据存 NVS（NVS 自带磨损均衡），图片内容走 store 裸槽；避免在运行期反复重写同一槽位。
