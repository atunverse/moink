## 0. 立项原则

1. **固件只做「传输 + 电源」**：热点、接收、刷图、休眠、唤醒、OTA。固件不做任何图像/文字处理、不做任何屏上合成。
2. **页面负责一切画面**：裁剪、色彩管线、抖动、2bpp 打包、文字便签，全部在浏览器 Canvas 完成，整帧下发。
3. **契约文档化**：底层契约（色码、几何映射、帧格式）写入 `docs/CONTRACT.md` 并配自动回归，不散落在注释里。
4. **模块单一职责**：帧接收、电源管理各自独立成模块，main 只做装配。
5. **每个里程碑必须上机验收**，不接受"编译通过就算完成"。
6. **功能导向重写**（用户明确要求）：以功能为目标重新思考实现，**不逐行照搬旧代码**；参考旧实现时必须先理解"它为什么这么写"，区分"真实 bug 换来的防御性检查（保留）"与"叠补丁产物（去掉）"。
7. **锁定模块清单**（用户明确冻结，只搬不改）：
   - **屏驱动**（A0 / A1 驱动序列、几何映射、BUSY 状态机）——已跑通；
   - **图像算法**（eink-warm 全套：幂律饱和度、色相加权、线性光抖动及全部默认参数）——已跑通且显示效果经用户确认，**暂时锁定不改动**。
   这两个模块是全项目唯二允许"已验证实现直接移植"的代码，且各配自动回归守护（色卡上机 / `check_algo` MATCH）。

## 2. 整体架构

```
┌─────────────────────────── 手机浏览器（一切图像处理） ───────────────────────────┐
│  选图 → 裁剪框(M5式选区+90°步进) → eink-warm(冻结) → 线性光抖动 → 2bpp打包(180°契约)│
│  文字便签 │ 残影清理 │ 设置(休眠/唤醒/热点) │ OTA 上传 │ 页面自更新 │ 版本展示     │
└───────────────┬─────────────────────────────────────────────────────────────────┘
                │ HTTP over SoftAP(192.168.4.1) + Captive DNS 引流
┌───────────────▼──────────────────── ESP32-C3 固件 ──────────────────────────────┐
│  接入层   http_server（路由/收发）   captive（:53 DNS + 探测劫持）                │
│  业务层   frame（16B头+CRC→fb）  ota_web（OTA/web分区）  settings（NVS）          │
│  电源层   power（ADC/深睡/定时唤醒/长按） ←→ main（装配 + fb 互斥交接）           │
│  驱动层   epd_drv（A0/A1 · 2bpp 全刷 · BUSY 状态机）【锁定移植】                  │
└───────────────┬─────────────────────────────────────────────────────────────────┘
                │ SPI + BUSY/RST
        ┌───────▼────────┐
        │  四色墨水屏面板  │  A0 768×552（隔行）/ A1 768×552（线性）
        └────────────────┘
```

- **单通道数据面**：唯一数据入口 `POST /api/frame`。删 STA 后 HTTP 面只剩 6 条路由（frame / settings / info / ota / web / 页面与落地页），并发压力极小。
- **无 STA 连锁简化**：WiFi 恒为 `WIFI_MODE_AP`，APSTA 切换、重连退避、配网状态机全部消失；lwip/heap 占用同步下降。
- **fb 互斥交接**：上传与刷屏共用静态 `s_fb[105,984]`，lock/unlock/len 交接模式保留（`moink_fb.h`）。

## 3. 模块划分与职责

### 3.1 固件（`src/`）

| 模块 | 职责 | 备注 |
|---|---|---|
| `main.c` | 启动装配、建任务、注册路由、持有 fb 与互斥量 | 启动顺序见 5.5 |
| `http_server.c` | 路由表 + 收发；`GET /` 页面分发（web 分区优先、内嵌兜底）；`/api/info`（版本/电量/heap） | 忙时 `send_busy`（IDF httpd 无 503） |
| `frame.c/h` | `POST /api/frame`：16B 头校验（0xA5 0x5A/版本/屏型/宽高/载荷长/CRC16）→ fb 锁写入 → 通知刷屏任务；**刷屏中拒绝新帧（409）** | |
| `epd_drv.c/h` | 屏驱动：A0/A1 初始化、2bpp 全帧、BUSY 双窗口（45s/180s）、面板深睡；**RST=GPIO3**（自 GPIO2 改来） | **锁定移植**，配色卡上机验收 |
| `netif_ap.c/h` | 纯 SoftAP：SSID/密码/信道/连接数管理；无任何 STA 代码 | 凭据来自 settings |
| `captive.c` | :53 DNS 全 A 记录 + OS 探测路径劫持 | |
| `ota_web.c` | OTA 双槽 + 回滚 + 45s 确认；`POST /api/web` 页面写 web 分区（CRC32）；`web_capacity()` 运行时读分区 | 方案见第 6 节 |
| `power.c/h` | 电池 ADC（GPIO0 分段曲线）、空闲休眠（可配）、深睡进入/唤醒原因、**定时唤醒**（RTC timer）、长按 5s 恢复出厂 | |
| `settings.c/h` | NVS：`sleep_s`、`wake_s`、`ap_ssid`、`ap_pass`、`hflip`；`GET/POST /api/settings` | 不存页面参数 |
| `moink_fb.h` | 帧缓冲互斥交接契约 | |

任务清单（静态创建）：httpd（系统）＋ frame 4096 ＋ captive_dns 3072 ＋ idle_mon 3072 ＋ button 3072 ＋ ota_confirm 2048。

**引脚映射**：RST=GPIO3（自 GPIO2 改来）、唤醒键=GPIO5、电池 ADC=GPIO0；SPI 的 MOSI/CLK/CS/DC、BUSY 等沿用旧板定义（以 `legacy_ref/` 中旧 `epd_drv.c` 为准，不在此臆造）。

### 3.2 `/api/settings` 设计

```jsonc
// GET /api/settings →
{ "sleep_s": 180, "wake_s": 0, "ap_ssid": "MoInk-A1B2", "ap_pass": "", "hflip": 0 }
// POST /api/settings（部分字段可省，仅更新出现的字段）
```

| 字段 | 取值 | 默认 | 说明 |
|---|---|---|---|
| `sleep_s` | 60 / 180 / 300 / 0（不休眠） | 180 | 空闲休眠时长，页面下拉「1 分钟 / 3 分钟 / 5 分钟 / 不休眠」 |
| `wake_s` | 0（关）/ 3600 / 43200 / 86400（可扩展） | 0 | **定时自动唤醒间隔**：深睡中由 RTC timer 定时唤醒，重新广播热点窗口（默认开 3 分钟）等人连接传图，无人连接则自动回睡 |
| `ap_ssid` | 1~32 字节 | `MoInk-XXXX` | 热点名 |
| `ap_pass` | 空=开放；8~63 字节=WPA2 | 空 | 热点密码 |
| `hflip` | 0/1 | 0 | A1 屏镜像兜底（锁定保留项） |

> **自动唤醒的语义与精度说明**：C3 的 RTC 慢时钟为内部 RC（无外置 32k 晶振），定时误差约 ±1%~2%——12 小时档实际唤醒可能偏 ±7~15 分钟。对"到点醒过来开热点"的用途可接受；**不建议**为了精度外挂 32k 晶振（增加硬件改动）。校准周期 `CONFIG_RTC_CLK_CAL_CYCLES` 保持 1024（为保唤醒间隔精度，**不做**官方启动提速文档里的"置 0"优化）。

### 3.3 分区表

**暂不修改**（用户明确）。沿用：`nvs 16K + otadata 8K + phy 4K + ota_0 1.5M + ota_1 1.5M + web 960K`。删除 STA/fetch 后 app 预计 ≤ 650 KB，槽位冗余极大。

| 契约 | 内容 |

## 5. 固件性能与功耗设计 ★

> 参考来源：Espressif 官方《Low Power Mode in Wi-Fi Scenarios》《Sleep Modes》《Speed Optimization》
> 及社区实测案例（Zero-Standby sensor、Picoclick C3 等开源项目的 sdkconfig 实测数据）。

### 5.1 功耗模型（ESP32-C3 参考数据）

| 模式 | 芯片电流 | 本项目适用性 |
|---|---|---|
| Active（WiFi TX 峰值） | 200~300 mA | 传图瞬间，秒级 |
| Active（AP 待机，含 beacon） | 80~120 mA | **唤醒期的主体功耗** |
| Light sleep | 130 µA（无外置 32k 时 RC 路线升至 mA 级） | **不采用**：AP 模式不支持 modem-sleep，light-sleep 挂 AP 无意义 |
| Deep sleep | ~5 µA（芯片级） | **主要待机状态**；整机电流由 LDO 静态电流主导，R2 实测 |

**核心结论（决定整个功耗策略）**：SoftAP 模式**不支持 modem-sleep**——AP 必须持续发 beacon，这是物理约束，无法在"保持热点"的同时省电。所以策略不是优化唤醒期的电流，而是**最小化唤醒期时长**：能睡就睡、睡满就走、传完即睡。

### 5.2 关键优化点与取舍

| # | 优化点 | 做法 | 收益 | 代价 / 取舍 | 决策 |
|---|---|---|---|---|---|
| 1 | 缩短活跃窗口 | 上传完成→面板回睡→按 `sleep_s` 回深睡；无人连接的热点窗口最多 3 分钟 | 平均电流数量级下降（如 3 分钟窗口每小时唤醒一次 → 占空比 5%） | 无 | ★ 主要手段 |
| 2 | 定时唤醒（新增） | RTC timer 周期唤醒，开热点窗口等人 | 挂件定期可用而无需按按键 | RC 时钟 ±1~2% 误差 | `wake_s` 可配，默认关 |
| 3 | TX 功率降到 18 dBm | `esp_wifi_set_max_tx_power` | 峰值电流降低、供电更稳 | 覆盖略减（挂件场景 1~2 m 足够） | 采用，R2 上机验证连通性 |
| 4 | beacon 间隔 | 保持 100 ms 默认 | 热点稳定（手机扫码/重连快） | 空口开销略增 | **稳定优先，不改** |
| 5 | 连接数限制 | `max_connection = 2` | 防滥用、内存可控 | 无 | 采用 |
| 6 | 深睡引脚处理 | 面板 0x07+A5 深睡、SPI/CS/RST 引脚 `gpio_hold` + 浮空脚 isolate | 消除引脚漏电 | 无 | 采用 |
| 7 | 深睡唤醒跳过镜像校验 | `CONFIG_BOOTLOADER_SKIP_VALIDATE_IN_DEEP_SLEEP` | 深睡唤醒省一次全镜像 SHA（百 ms 级） | 唤醒时 flash 损坏风险极低（deep-sleep 前系统已验证过） | 采用 |
| 8 | 上电校验 | `SKIP_VALIDATE_ON_POWER_ON` **不启用** | — | 上电保留完整校验，安全优先 | 不采用 |
| 9 | Flash 时序 | DIO 40M → 试 QIO 80 MHz | 镜像加载提速（案例：标准 ~300 ms → ~70 ms 级改善） | 板载 flash 兼容性需实测 | R1 实测决定，失败即回退 DIO 40M |
| 10 | 日志降级 | 生产 `CONFIG_LOG_DEFAULT_LEVEL=Error` + bootloader log=Error | 启动提速 + 省电 + 省体积 | 排障能力（保留编译开关随时切回 Debug） | 采用 |
| 11 | RTC 校准 | `RTC_CLK_CAL_CYCLES=1024` 保持 | 定时唤醒精度 | 牺牲少量启动时间 | 保持（见 3.2 说明） |
| 12 | ROM 打印 eFuse | `UART_PRINT_CONTROL` 烧录 | 省几十 ms | **不可逆**、收益小 | **不做** |
| 13 | CPU 降频 / DFS | 不做 | — | 活跃窗口短，复杂度 > 收益 | 不做 |

### 5.3 热点稳定性要点

- 固定信道 1、beacon 100 ms、`max_connection=2`、DHCP 小地址池。
- **任何刷屏动作绝不挂在连接/断开事件上**（M7 引导条的教训）；客户端频繁断连重连不影响设备状态机。
- fb 忙（刷屏中）→ 新帧请求 409 + `Retry-After` 语义，页面提示重试；httpd 并发用互斥串行化。
- `frame` 任务刷屏期间 BUSY 等待分片 `vTaskDelay` 喂狗（长等待不能阻塞 IDLE）。

### 5.4 深睡与唤醒路径

```
深睡进入：面板 0x07+0xA5 → 引脚 hold → (可选)配置 RTC timer wake_s → esp_deep_sleep_start
唤醒源：  GPIO5 按键（低电平） | RTC timer（wake_s>0 时） | 复位
唤醒流程：读 esp_sleep_get_wakeup_causes() bitmask
          → 按键唤醒：正常启动（不碰玻璃，直接出热点）
          → 定时唤醒：同样出热点窗口；窗口结束无人连接 → 立即回睡（不重刷屏、不重读 NVS 大表）
```

唤醒即出热点、不刷任何屏（M7 二稿已验证此路径成立），目标**深睡唤醒→热点可连 ≤ 1 s**。

### 5.5 上电/启动速度

目标：**上电→热点可连 ≤ 1.5 s**。启动顺序（关键路径上只留必要项）：

```
NVS init → fb/互斥 → epd GPIO+SPI init（不碰玻璃）→ netif_ap 启动 → http_server → captive DNS
→ 其余全部延后：ota_confirm 任务、电池 ADC 首采、idle_mon 计时
```

sdkconfig 生产清单：`LOG_DEFAULT_LEVEL=Error`、`BOOTLOADER_LOG_LEVEL=Error`、`BOOTLOADER_SKIP_VALIDATE_IN_DEEP_SLEEP=y`、`BOOTLOADER_LOG_BOOTLOADER_OPT=-O2`、flash 时序 R1 实测定。**eFuse 级优化一律不做**（不可逆）。

## 6. OTA 升级与安全方案 ★

### 6.1 升级流程（可靠性优先）

```
页面选包 → 预检（读取新包 app_desc：magic/芯片型号/最小 eFuse/版本，降级需显式确认）
→ [互斥检查：刷屏中/帧传输中 → 拒绝（409）]
→ esp_ota_begin(已知总长) → 分块写入（4 KB/块，块间让出 CPU）
→ esp_ota_end（自动做 SHA-256 + 镜像结构校验）
→ esp_ota_set_boot_partition(新槽) → 重启
→ 新槽运行 → ota_confirm 任务 45s 窗口内收到 /api/info 心跳即 mark_app_valid
→ 超时未确认 → 自动回滚旧槽（rollback 机制）
```

### 6.2 可靠性设计点

| 机制 | 说明 |
|---|---|
| 双槽 + rollback | ota_0/ota_1 互为备份；新固件未经确认，otadata 不指向它；断电/崩溃自动回旧槽 |
| 写入完整性 | `esp_ota_end` 原生 SHA-256 校验，坏包根本进不了启动路径 |
| 中途失败 | HTTP 断开 → `esp_ota_abort`，当前槽不受影响，正在运行的系统毫发无伤 |
| 互斥 | OTA 与刷屏互斥（都动大块资源）；OTA 期间拒绝新帧，反之亦然 |
| 确认窗口 | 45s 心跳确认；同时要求页面显示"新固件版本号"让用户目视核对（第 8 节版本体系） |

### 6.3 "OTA 不影响性能和启动速度"的论证（用户要求）

- **运行时零开销**：OTA 只写 flash 内容，不改变任何运行路径。写 flash 期间的 cache-miss 停顿仅存在于升级那几分钟，且通过分块写入 + 让出 CPU 控制在可感知阈值以下；升级完成后系统与升级前完全一致。
- **启动零负担**：分区表不变、槽切换只是 otadata 读向。若启用上电跳过校验才有感知——本项目**上电校验保留**，启动路径与未升级过完全相同。
- **web 分区页面热更同理**：`POST /api/web` 只写 web 分区，与 app 无关，甚至不需要重启。

### 6.4 安全启动（Secure Boot v2）/ Flash 加密：**不启用**

理由：① 烧 eFuse **不可逆**；② Secure Boot 会给每次启动加签名校验（与"启动速度"目标冲突，也与优化点 #7 冲突）；③ 威胁模型不匹配——OTA 只发生在自建热点局域网内、无远程入口，攻击面是"能连上我热点的人"，用可选热点密码 + 回滚机制已足够。文档记录此决策与未来重新评估的条件（若产品化对外发行再议）。

## 7. 页面设计

### 7.1 图像算法：冻结移植

- M7 页面的 eink-warm JS **原样搬入**，代码区块加 `/* ===== FROZEN: eink-warm algorithm — do not modify ===== */` 边界注释；参数默认值逐项保持。
- 守护：`check_algo.js`（页面 JS）vs `check_algo.py`（真源 `eink_warm.py`）双端逐像素比对，要求 **MATCH**；任何触碰冻结区的改动都必须先跑 MATCH 才算完成。
- 用户对显示效果已确认满意，"好看"本身是验收标准。

### 7.2 裁剪：回归 M5

| 项 | M5（回归目标） | M7（废弃） |
|---|---|---|
| 选区 | 裁剪框：固定屏幕比例，单指拖动 + 捏合缩放 | 同左（保留） |
| 旋转 | **90° 步进**（方向按钮组 0°/90°/180°/270°，默认 90°） | 框内角度条 360° + ±4° 吸附 + 无白角 AABB 反解 |
| 数学 | 简单可靠，无白角问题 | 任意角度反解复杂（已出过几何 bug） |

实施期参考 `legacy_ref/` 中的 M5 裁剪代码，**理解其选区→画面换算后重写**，不照抄（第 0 条原则 6）。

### 7.3 功能结构（清理后的三段式）

```
① 图像区   预览画布 + 裁剪框 + 方向按钮组 + [上传并刷新屏幕]
② 风格区   画面风格(4) / 色彩强度 / 文字(字体/字号/颜色/内容) / [高级图像设置(默认收起)]

```

**移除的低频/过时入口**：模式切换以外的冗余按钮合并入设置区；旧版残留的画廊相关项已不存在；离线导出、OTA、页面更新、残影清理全部收进「维护」分组，不再散落主界面。设置项持久化 `localStorage`（`moink.cfg4`，新项目无迁移负担）。

## 8. 版本管理 ★（固件与页面分离）

### 8.1 三层版本号

| 版本 | 载体 | 上报 | 规则（语义化） |
|---|---|---|---|
| **API 版本** | 帧格式 + 路由契约 | `/api/info` 的 `"api"` 字段 | 整数，**从 1 起**；帧格式沿用已验证的 16B 头 + 2bpp 定义（仅在新体系编号为 1）；不兼容改动才 +1 |
| **固件版本** | `PROJECT_VER`（写进 app_desc，OTA 预检可读） | `/api/info` 的 `"fw"`，如 `"R1.0.0"` | MAJOR=契约/API 破坏性变更；MINOR=固件功能；PATCH=修复 |
| **页面版本** | 页面 `<meta name="moink-page-version">` | 固件解析 web 分区页面 meta 后随 `/api/info` 的 `"page"` 上报；web 分区为空则报内嵌页版本 | 同上，独立于固件演进 |

### 8.2 升级判断流程

```
页面加载 → GET /api/info → 显示 fw / page / api 三项版本（设置区"设备"卡片）
│
├─ 页面有新版（发布说明对照）且不含固件接口变更
│    → 维护区上传新 html → POST /api/web → 即时生效，无需刷机 ★ 核心收益
│
├─ 固件有新版
│    → 维护区上传 moink_app.bin → POST /api/ota → 重启 → 45s 确认
│    → 页面重载后核对 "fw" 已变化
│
└─ 防错配（自动检查）
     页面所需 API 版本 > 设备 "api" → 页面顶部横幅："固件过旧，请先 OTA"
     固件页面 meta 解析失败        → 视为未知版本，横幅提示重新上传页面
```

**判据（写入 CONTRIBUTING 说明）**：改动是否涉及固件 = 是否动了 帧格式 / 路由 / 契约 / 固件接口字段。没动 → 纯页面发布，只走 `/api/web`；动了 → 固件 MAJOR 或 MINOR，走 OTA，页面同步发版。

### 8.3 版本号起点

新项目从 **`fw R1.0.0` / `page R1.0.0` / `api 1`** 起（`R` = 重构里程碑 R 系列，与旧 M 系列区分）。`PROJECT_VER` 直接写 `R1.0.0`（作展示串即可；OTA 防降级不依赖纯数字版本，靠用户显式确认）。


### 10.2 里程碑（压缩为 2 阶段：一次性开发 + 一次性上机验收）

> 针对「本机编译慢」：把所有**不依赖硬件的验证前置到编译之前**（零编译成本），固件 + 页面一次性写完，
> 全量编译一次、刷机一次，上机用一张合并清单完成综合验收。

| 阶段 | 内容 | 交付物 |
|---|---|---|
| **R1 一次性开发** | ①离线自测前置：`check_algo` MATCH、`smoke_page` 全绿、`check_frame` 金标准（均零编译、秒级）；②一次性写完固件 10 模块 + 页面（冻结算法 + M5 裁剪 + 三段式）+ 工具脚本 + CONTRACT 契约文档；③全量编译一次（QIO 80M 首版即定：`package_bins` 先切、失败回退 DIO 40M） | `moink_merged.bin` / `moink_app.bin` |
| **R2 上机综合验收 + 收尾** | 刷机一次，按合并验收清单逐项勾选；发现问题仅增量重编个别文件（rename 单个 `.o` 绕过 SAFE_DELETE）；通过后写刷机文档、锁定版本 | 验收通过的固件 + 文档 |

**上机综合验收清单（一次通电尽量全勾）**

1. 上电 → 热点 ≤1.5 s（SSID=`MoInk-XXXX`，默认开放）
2. 传图：传一张测试帧 → 3 s 内上屏、四色正确（顺带验色码 / 180° / A0 隔行契约）
3. `/api/settings`：改休眠 / 自动唤醒 / 热点 SSID 密码 → 重启后持久生效
4. 定时唤醒：设短档触发（测试期临时调小）→ 醒来开热点窗口 → 无人连接自动回睡
5. OTA：传新 app 包 → 重启 → 45 s 确认生效；再传坏包验证回滚不砖
6. 页面热更：`/api/web` 传新 html → 刷新即生效，不刷固件
7. 深睡功耗粗测（万用表待机电流）+ 唤醒→热点可连 ≤1 s
8. 长稳：连续传图 **30 张**（替代原 100 张，足够暴露泄漏/崩溃）看 heap 曲线

**编译次数预算**：目标 1 次全量出首版；仅 R2 上机发现问题才增量重编，最多再 1 次全量。
**兜底**：屏驱动是锁定模块（已在旧板 A0 跑通），首上电异常概率低；若真异常，才临时用「最小亮机固件」隔离排查，不作为常规里程碑。
