## 0. 开工前已核实的三个事实

| 事实 | 核实方式 | 影响 |
|---|---|---|
| 设置是**逐键**存 NVS（`nvs_get/set_u8/u32/str`），不是整块 blob | `src/settings.c:82/95/98/162/167/172` | 新增字段**零迁移**：老固件 NVS 里没这些键，读不到就用默认值，现有设置一项不丢 |
| `frame_display_now()` **内部会取** `s_fb_mutex`，而 `frame_display_slot()` 是自己取锁后直接调 `epd_display_2bpp_wh()` | `src/frame.c:52-75` / `285-310` | 远程取图**必须照抄 `frame_display_slot` 的写法**；若先取锁再调 `frame_display_now()` = **自死锁** |
| 本地轮播 `carousel_next()` 刷屏失败时**不推进 cur** | `src/main.c:760-778` | 远程轮播照抄这条：下载/校验失败不能把 `r_slot` 前移，否则下次唤醒跳过一张 |

## 1. 「能读」和「能写」是两种能力（先说清，避免后面踩空）

| 操作 | 协议要求 | 支持的服务 |
|---|---|---|
| **显示**（GET `.bin`） | 只要 HTTP GET | 任何静态 HTTP 目录、WebDAV、CDN、GitHub raw |
| **上传**（PUT `.bin`） | 必须支持 PUT | WebDAV（飞牛/群晖/Alist）、nginx-dav、少数对象存储 |

⇒ **普通静态 HTTP 目录只能当「只读图槽」**：能在上面放图让设备显示，但页面上的「存到远程」会失败。
你说「只要能读写就行」是对的 —— 读写都需要的场景，就必须选 WebDAV 类服务。设备端代码对两者一视同仁，只是服务器能力不同。

## 2. 阶段拆解

### P0 · APSTA 连路由器 + 设置项

**目标**：设备能连家里 WiFi，拿到 IP；热点照旧可用；连不上不影响本地使用。

| 文件 | 改动 |
|---|---|
| `src/settings.h` | 结构体加 `char sta_ssid[SETT_SSID_MAX]; char sta_pass[SETT_PASS_MAX]; uint8_t net_on;`（复用已有 33/65 上限） |
| `src/settings.c` | 加三个键的读/写/默认（`sta_ssid` / `sta_pass` / `net_on`），照现有 `get_str/set_str` 写法 |
| `src/netif_ap.c` | `WIFI_MODE_AP`（:112）→ `WIFI_MODE_APSTA`；`esp_wifi_set_config(WIFI_IF_STA, …)`；注册 STA 事件做重连 |
| `src/netif_ap.c` | **AP 信道跟随**：`ap.ap.channel`（:125）在 STA 拿到 IP 后改成 `esp_wifi_get_channel()` 的结果 |
| `src/main.c` | `/api/info` 加 `sta_ip` / `sta_rssi`；新增 `POST /api/net`（保存 + 试连） |
| `page/index.html` | 设置页加「WiFi 名称 / 密码 / 启用」三栏 + 连接状态显示 |

**风险**
- 改 AP 信道会让已连的手机**短暂断连**（约 1~2 s），要放在 STA 连上之后、且只改一次。
- STA 连接失败必须**静默**回退纯 AP，不能在页面上报错或阻塞启动（弱网/密码错是常态）。
- 页面固化三件套：改页面 → `make_index_header.py` → 才编译。漏第二步会静默打进旧页面。

**验收**：`/api/info` 出现 `sta_ip`；拔掉路由器热点仍在、页面能开；升级后原有设置全部保留。

### P1 · 远程取图最小闭环（单张 `.bin`）

**目标**：配一个 URL，唤醒就拉这张图刷屏；失败回退本地槽。

**新文件** `src/net_fetch.c / .h`，只暴露一个函数：

```c
/* 成功：已刷屏并深睡面板，返回 0；任何失败返回非 0（调用方回退本地轮播） */
int net_fetch_display(void);
```

内部（**照抄 `frame_display_slot` 的锁结构**）：

```
xSemaphoreTake(s_fb_mutex, 5s)            ← 先取锁
esp_http_client GET url（Basic 可选）
  → 先读 16 B 头：校验 0xA5 0x5A / 版本 / 宽高 / len 自洽 / epd_frame_geom_ok()
  → 再流式读 len 字节进 s_fb+16，边读边算 CRC16
  → CRC 不符 → 放弃
s_fw/s_fh 赋值 → epd_display_2bpp_wh(s_fb+16, w, h)
xSemaphoreGive(s_fb_mutex)                ← 再放锁
r==0 → epd_panel_deep_sleep()             ← 放锁之后才睡，与现有实现一致
```

**关键约束**
- **绝不能调 `frame_display_now()`**（它内部再取同一把锁 → 自死锁）。
- 下载全程持锁（5~30 s），期间 `/api/frame` 上传会 5 s 超时返回 busy。这是可接受的已知副作用：远程同步与手动上传本来就不该并发。
- 客户端配置：`buffer_size = 4096`、`timeout_ms = 30000`、不开 TLS（v1）、`HTTP_AUTH_TYPE_BASIC`（填了用户名才设）。

| 文件 | 改动 |
|---|---|
| `src/net_fetch.c/.h` | 新增，约 200 行 |
| `src/settings.h/.c` | 加 `remote_url[192]` / `remote_user[64]` / `remote_pass[64]` / `remote_on` |
| `src/main.c` | 唤醒路径：`if (remote_on && url[0]) { if (net_fetch_display() != 0) carousel_next(); } else carousel_next();` |
| `page/index.html` | 设置页加 URL / 账号 / 密码 / 「立即同步」按钮 |

**RAM**：`esp_http_client` 4 KB 缓冲 + socket ≈ 8~10 KB（无 TLS）。现有余量够，但要实测确认（见 §4）。

**验收**：改远端 `.bin` → 下次唤醒画面变化；URL 写错 / 拔网 → 画面不动、不白屏、回退本地槽。

### P2 · NAPT（热点转发）

**目标**：手机连设备热点也能上网。

| 项 | 改动 |
|---|---|

### P4 · 远程图槽全量（manifest + 多图 + 上传转发）

**目标**：远程目录不限量存图，设备按序轮播；页面上传可直接存到远程。

#### 4.1 `moink.mf` 解析（约 150 行）

```
GET moink.mf（限制 4096 字节，超限即拒）
  → 逐行扫描：第一行必须是 MOINKMF1；读 count / cur；数到第 target 行取「名 + CRC32」
  → 只保留 1 个文件名（≤64 B）和 1 个 CRC32，不建数组 ⇒ 内存固定
```

#### 4.2 远程轮播 `remote_next()`（照抄 `carousel_next` 的失败语义）

```
target = (cur >= 0) ? cur : (r_slot + 1) % count
若 manifest[target].crc == r_crc 且 target == r_slot → 直接返回（不下载、不刷屏）
否则 GET <name> → 走 P1 的下载/校验/刷屏逻辑
成功后才写 NVS(r_slot, r_crc)；失败一律不推进
```

#### 4.3 上传到远程（`/api/frame?save=remote`）

```
现有：收满 s_fb → 校验 CRC（不改）
新增分支：
  ① PUT  <根>/moink/<时间戳>.bin      ← 图已在 s_fb 里，直接用
  ② GET  <根>/moink/moink.mf          ← 读回现有清单（404 视为空）
  ③ 本地拼接（4 KB 缓冲）：count+1，末尾追加一行「文件名 CRC32」
  ④ PUT  回去
  ⑤ 成功 → 用手里的帧刷屏；失败 → 502，图仍在内存，可选择改存本地
```

**为什么 manifest 归设备维护**：生成端是网页手动上传，没有人会去改 `moink.mf`。让设备在 PUT 完图后顺手更新，用户全程无感。

**风险**
- **读-改-写不是原子的**：两个客户端同时上传会互相覆盖。单用户设备可接受，用一把 mutex 串行化即可；真要并发就得服务器侧处理（服务端脚本接管后自然解决）。
- 设备此刻是「手机 → 设备 → 路由器 → 远程」的中继，106 KB 传输约几秒（单射频分时），必须给足超时（建议 60 s）。
- 文件名用时间戳（`u_20261105_1802.bin`），避免与网页导出的 `0001.bin` 撞名。

**验收**：远程放 12 张 → 设备按序轮播一圈回到第 1 张；页面选「存到远程」→ 远端多一张、本地 8 槽不变；删除远端某张并改 manifest → 设备不崩、按新清单轮播。

## 3. 内存与体积预算

| 项 | 增量 | 说明 |
|---|---|---|
| `moink_settings_t` | +482 B | 4 个字符数组 + 2 个开关，静态 RAM |
| `esp_http_client` 运行时 | +8~10 KB heap | 4 KB 缓冲 + socket，无 TLS |
| manifest 解析缓冲 | +4 KB heap（可静态） | 只在 P4 |
| Flash（代码） | +25~35 KB | `esp_http_client` + 我们的 ~500 行 |
| Flash（余量） | 现 986/1280 KB（77%）→ 约 81% | 仍有余量，但 P4 后要盯紧 |

## 4. 每个阶段动码前必须实测的两项（§8 遗留）

1. **AP 模式真实 free heap**：刷现有固件 → 连热点 → `GET /api/info` 看 `heap` 字段。
   P1 要 +10 KB、P2 要 +8~16 KB、P4 再 +4 KB，必须确认总和有余量。
2. **AP 信道跟随是否影响已连客户端**：手动改路由器信道，观察手机是否需要重连。

## 5. 建议节奏

```
P0（APSTA）→ 真机验证 → P1（单张 .bin）→ 真机验证
   → P2（NAPT）→ 真机验证 → P4（远程图槽）
```

P0 和 P1 各自独立就有价值（P0 让手机和电脑同网访问设备；P1 让图能自动换）。
P2 收益直观但坑最多（门户、信道、RAM），P4 依赖 P0+P1 都稳。

## 6. 本方案明确不做的事

- 不做设备端 JPEG 解码（§4.1.1 已否决）
- 不做 PROPFIND / 列目录（manifest 替代）
- 不做远程 + 本地双写
- 不做 TLS / 证书校验（v1；后续要 https 再评估，代价是 +80~110 KB flash 与握手 RAM）
- 不做多用户并发写 manifest（单用户设备）
