# MoInk 未实施项说明

> 基线：fw R1.0.8 + page R1.0.22（2026-09-18 批量审查修复后的版本）
> 来源：《代码审查报告-2026-09-18.html》中列为「建议实施」但本次批次**有意跳过**的效率打磨项，以及审查后**明确不建议动**的结论项。
> 性质：以下全部为**效率/打磨类**改动，无一是正确性缺陷；跳过不影响功能与稳定性。

---

## 一、主动搁置的 5 项

### 1. 图像管线 Float64 → Float32（收益最大、最敏感）

| | 说明 |
|---|---|
| 现状 | 预览合成链路 toBuf → warmMap → blur3 → quantize 全程 `Float64Array`；552×768 全幅时单个 n×3 缓冲 ≈ 10MB，峰值内存约 40MB |
| 影响 | 老手机浏览器切大图时可能 GC 卡顿，极端情况标签页被杀 |
| 拟改 | 全链换 `Float32Array`（精度远超 8bit 输出需求，理论数值行为不变）；删 quantize 里 `new Float64Array(mapped)` 整份拷贝（warmMap 输出无第二处引用，可原地加误差） |
| 搁置原因 | 触碰**逐行冻结的 eink-warm 算法**（check_algo.py 12/12 MATCH 锁定）。累加顺序变化可能让个别像素在四色边界吸附到不同颜色——肉眼未必可见，但违反冻结铁律 |
| 实施条件 | 改后必须：check_algo 全 MATCH + 多张真图逐模式（natural/adaptive/gray/naive）逐像素对比出图一致 |

### 2. OTA 上传流式擦除（固件响应性）

| | 说明 |
|---|---|
| 现状 | `ota_handler` 收到上传请求即 `esp_ota_begin`，同步整槽擦除 1.5MB flash（约 2~4 秒），期间 HTTP 无响应 |
| 影响 | 点上传后浏览器转圈数秒才开始有进度，纯体验问题 |
| 拟改 | 参照 web 分区「按扇区先擦后写」模式，begin 只登记、擦除分摊到 `esp_ota_write` 逐扇区，首字节响应提前数秒 |
| 搁置原因 | OTA 是**少数已上机完整验证的功能**；流式擦写=重写 OTA 写入路径，扇区边界失误（教训⑧静默损坏）可能刷一半变砖、只能 USB 救 |
| 实施条件 | 单独一版固件只改这一件事，专测 OTA 全流程 |

### 3. saveCfg 每键全量写 localStorage（写盘压力）

| | 说明 |
|---|---|
| 现状 | 滑杆/打字每个 input 事件都全量 JSON 序列化写 localStorage（含两个文字对象数组），快速拖动一秒写几十次 |
| 影响 | 实际卡顿感知极低（localStorage 写入很快），主要是写放大 |
| 拟改 | saveCfg 加 300ms 尾触发节流 + `beforeunload` 兜底写一次 |
| 搁置原因 | 引入**新的失败模式**：300ms 窗口内页面被系统回收（手机切后台），最后一次设置会丢，兜底必须正确才算闭环 |
| 实施条件 | 与 Float32 批次一起做，回归设置保存/刷新回显 |

### 4. relayoutOne 拖动每帧重建手柄 DOM（拖动期 GC）

| | 说明 |
|---|---|
| 现状 | 文字拖动时每帧（rAF）清空重建 4 个手柄（删除/旋转/宽度/缩放），持续小对象垃圾 |
| 影响 | 长拖动可能有轻微 GC 抖动（实测流畅，收益接近零） |
| 拟改 | 手柄在对象创建时生成一次，relayoutOne 只更新 left/top/width/height |
| 搁置原因 | 这段交互是 R1.0.15~R1.0.19 五版调教出的**单视觉源架构**，刚经上机验证稳定；DOM 复用重构涉及手柄生命周期（删除时清理/切模式重建），回归面覆盖全部文字手势 |

### 5. cropCache 单槽改双槽（裁剪缓存命中）

| | 说明 |
|---|---|
| 现状 | 裁剪缓存单槽：预览用半分辨率（fast）、最终合成用全分辨率（full），key 不同**交替互踢** |
| 影响 | 预览↔合成切换时重复一次 canvas 缩放重算（几十毫秒级） |
| 拟改 | 按 (sig, 宽, 高) 双槽，或 fast 预览直接从 Cropper 原图缩放 |
| 搁置原因 | 收益中等，但触及裁剪→预览→上传核心数据供给路径；建议与 Float32 管线同一版本做（同在图像管线，一次回归测完） |

## 二、明确「不建议动」的 3 项（结论，非遗漏）

| 项 | 不动的理由 |
|---|---|
| frame.c / ota_web.c 各自的 CRC16/CRC32 | 看似重复，但各自仅一处使用，且算法**冻结在帧格式契约**里；抽公共函数破坏「与契约文档 1:1 可读性」 |
| epd 驱动「整屏填色/写行」逻辑相似 | `epd_clear_cycles` 与写帧函数可抽公共函数，但驱动序列是 A0 隔行映射的 1:1 移植约定，抽象后任何参数传递错误直接花屏，**冻结优先** |
| renderComposite 结果不缓存 | 每次上传前重新合成保证「所传即所见参数终态」，是**正确性设计**；缓存可能把中间态参数的画面传上去 |

---

## 三、后续实施建议

1. **一次专门的页面版本**（暂名 page R1.0.23）：Float32 管线 + cropCache 双槽 + saveCfg 节流 + relayoutOne 手柄复用——统一回归套件（check_algo + 真图逐模式对比 + 手势实测 + 设置保存实测）一次测完。
2. **OTA 流式擦除单独一版固件**（暂名 fw R1.0.9）：只改这一件事，专测 OTA 全流程（上传/回滚/防降级）。
3. 在上述版本实施前，**fw R1.0.8 + page R1.0.22 可放心上机使用**。
